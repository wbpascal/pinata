# Byte-compatibility is proven by capture replay

Every capture is converted once into a transcript: a committed text file under `test/replay/transcripts/`, one line per decrypted packet with capture timestamp, connection, direction, opcode and payload. The `.pcapng` stays the source; the conversion extends `tools/protocol-re/pcap_decode.py`, and the Elixir side never parses pcap. A replay test builds the capture's starting state, sends the transcript's client packets through the test client, and requires every server packet to equal the transcript's byte for byte outside the masks.

We compare bytes, not decoded structs, because comparing structs would run both sides through the codec under test and hide its errors.

**Pacing and strictness.** Client actions (open, send, close) run in the capture's overall order, each after all earlier server packets have arrived. Server packet order is checked per connection only, never across connections and never by timing. A missing, extra or reordered server packet fails the test, except for a short declared list of timer-driven opcodes (heartbeat, `0x080E` game time) accepted at any position. A replay test names a stop point in its transcript, moved forward as later milestones land.

**Values that cannot match.**

- Session values (seed), server addresses (`0x0C0C`, `0x1003`, `0x180A`) and fields the original server fills with uninitialised memory are masked. The rebuild sends zeroes for the last kind. Login tokens and the validation key are not masked: they go through the handle map below.
- Handles, item keys, login tokens and the validation key of `0x0C0C` (the client sends it back in `0x0C0F`) go through a handle map: the first pairing of an original value with a new one is bound, every later occurrence must agree. This checks consistency without copying the original's allocator. Object handles are bound per map, taken from the captured map name at each Zone entry, because the original allocates per zone process and the rebuild per map instance; both clients of a capture share that scope. `0xFFFF` (no target) passes unmapped.
- Clock values are compared, not masked. Server code reads time and randomness only through a `Clock` and a `Random` module; a custom Credo check in `mix check` rejects direct calls elsewhere. Before each transcript line, client or server, the harness moves the injected clock to that line's capture timestamp, so replay never sleeps. A map instance schedules its tick through `Clock`; the test clock fires every due tick in order and waits until the map instance has run it. Only the tick is scheduled this way: heartbeat, game time and auto-save stay real timers. After each Zone client packet the harness does a heartbeat round trip before the clock moves on. The original's tick phase is unknown, so a test whose transcript shows a tick-driven packet on the wrong side of an answer declares a tick offset in milliseconds; order stays strict. A replay may also declare `late_ms:`: the clock then runs up to that far ahead of a Zone server line that has not arrived, and never backwards.
- Random game values (damage, drops) are decided with the combat milestone.

Masks are named by field and resolved to byte ranges through the packet definition. They live in one global list, each with its reason (and the bug id for uninitialised memory); a test may add its own with a reason.

**Later milestones inside a capture.** Deferrals sit in a second list next to the masks, each naming the milestone that removes it. Besides a payload or a server packet, a deferral can leave a client packet unsent, with its answers absent, so a replay continues past a stretch of a later milestone. A deferral can also drop server packets the rebuild sends as placeholders where the original sends none (the empty item boxes of `0x1047` until milestone 3). The state is never patched in the middle. If the skipped stretch changes something a later compared packet shows, the changed fields get deferrals of their own where they can be named (scenario 45: `Equ_LeftHand` and `abstatebit` of `0x1C06`); otherwise the test declares a replay cut: an end time before the capture's end, with a one-line reason. A replay cut is also declared where the rebuild answers differently on purpose (a fixed original-server bug) or where the capture needs an operator action the harness cannot do (a killed zone process, server data changed in the middle). What lies behind a replay cut and belongs to the milestone gets a hand-written test whose expected bytes are copied from the capture; nothing is recorded again for it. Until milestone 4 mobs are deferred by object: the harness reads each captured appear (`0x1C08`, the elements of `0x1C09`); a mob id that is an NPC row of that map is compared, any other handle is excluded until its `0x1C0E`. Every captured server packet about an excluded handle is taken out, `0x1C09` is reduced to its NPC elements, and a client packet that targets an excluded handle is not sent.

**Two clients.** A capture with two clients is one transcript; its clients are just more connections. The transcript cannot tell which client a connection belongs to, so the test names the packets after which a Zone connection closes at a map change.

**Starting state.** One Elixir setup function per capture, written from its scenario notes, using public `Persistence` operations where one exists and a test-only factory for the rest. No database dumps, so the same setup runs on SQLite and PostgreSQL. `Persistence` is validated by replay (reads, write-then-read sequences, and the end state where the capture has a database snapshot) plus a direct test per business operation including every guarded-update refusal.

**Test client.** One library (socket, framing, cipher, codec, expect helpers) serves both replay and hand-written end-to-end tests. It speaks TCP only and connects to whatever address the server sends.

**Where no capture exists.** Every client-facing handler branch is hit by a replay test or by a hand-written end-to-end test whose expected bytes come from the reconstruction in `docs/`. A later capture that disagrees wins and replaces the hand-written test. Behaviour that needs a timeout to elapse is tested by hand with the timeout shortened in the settings.

**Topology.** Tests only speak TCP, so one environment variable picks the mode: single-node starts all parts in the test VM on SQLite; multi-node starts Login, WorldManager and Zone as `:peer` nodes on PostgreSQL. We chose `:peer` over containers for the suite because each replay test needs a fresh database and its own clock start; containers would need a restart per test or a test-only control port in the release. CI adds one Docker Compose smoke test (three part containers, PostgreSQL, one hand-written login-to-character-list run) to prove the real release; its compose file is the multi-node example in the user documentation.

## Consequences

- No server code may call the system clock or `:rand` directly, from the first line written.
- Every new mask is a claim that a field cannot match; reviewers check the reason.
- The multi-node suite does not exercise the release artifact; only the smoke test does.
- A capture is fully replayed only once the last milestone it touches is done.
- Timer intervals themselves (how often a heartbeat fires) are not proven by replay.
