# D02 knowledge: Character server (characters, avatars, save/load)

Facts other items need. Details and evidence: `docs/pseudocode/db/D02-character.md`. Names:
`tools/protocol-re/names/character/D02.json` (all 310 `{CALL}` wrappers are named `SQL_<procedure>`; DB getters, send
helpers, globals). Layouts: `docs/protocol/annotations/D02.json` (key `character`; `packets.py` does not render the
character server yet, so the generated docs do not show them).

## Framework (for D03 / D04)

- Same "DataServer" as Account/AccountLog (D01): one ODBC connection per worker at handler `*this + 0x124c`;
  `CheckAlive` @ FUN_0043c640; replies on the requesting link.
- Result getters (column index auto-increments): `DB_Fetch` FUN_0044fb90, `DB_CloseCursor` FUN_0044fbc0, `DB_GetI32`
  FUN_0044fbd0 (C type -16), `DB_GetU8` FUN_0044fc00 (-28), `DB_GetU16` FUN_0044fc30 (-17 = SQL_C_USHORT), `DB_GetU32`
  FUN_0044fc60 (-18), `DB_GetI64` FUN_0044fc90 (-25), `DB_GetU64` FUN_0044fcc0 (-27), `DB_GetStr` FUN_0044fcf0 (1),
  `DB_GetBin` FUN_0044fd40 (-2), `DB_GetTime` FUN_0044fda0 (11, TIMESTAMP_STRUCT). Bind direction 1 in, 2 in/out, 4 out.
- Sends: `CSendPacket_SetOpcode(op, payloadSize)` FUN_0044fa10 (size **includes** the 2-byte handle prefix; one
  exception, 0x1416, is 2 short), `Session_SendPacket` FUN_0043d5f0, `Session_SendRaw` FUN_0043d620, GameLog link
  `g_GameLogLink` DAT_006ecee0 (sent with FUN_0044ce10; the server refuses incoming S2S links until it is up).
- `MakeItemKey` FUN_004041d0 (time-packed u64 + counter DAT_006edd54); `Item_Insert` FUN_0046be10 (4th arg 1 =
  `p_Item_Create_UseEmptyStorage`); `ItemAttr_Init` FUN_00467940; `ItemLotAfterUse` FUN_004038c0; `ItemList_ByStorage`
  FUN_00469f70 (`p_Item_GetListType`, rows {u64 key, u16 slot, u32 itemId, u32, ts}, 40-byte records).
- Run-time call strings exist (`SQL_BuildCallString` FUN_00460bf0, e.g. `p_Char_SetStateWithSetItemAndRestTime`), so
  `bak.py cover` misses some procedures.
- GameLog packets sent from these handlers: 0x040A login, 0x040B logout, 0x0412 delete, 0x0420 class change, 0x044F
  item create, 0x0459 / 0x045A item use lot / all, 0x0658–0x0660 wedding.

## Answers to open questions

- **Z07 §5 wedding partner:** the Character server never chooses a partner. `0x1083 PROPOSE_REQ {hdr6, u32 Partner}`
  stores the number the zone sends into both `tMarriage` rows (`nStatus 1`, `dSubWhen = now + 3 days`).
  `Partner.RegisterNumber` in `0x1081` is `tMarriage.nPartnerCharNo`, which no cancel / escape / divorce procedure
  clears: after those it is still the old partner. A single character (no row partner) gets `Error 0x12E2`.
- **Z07-B11 divorce Success 0:** `0x1089` / `0x108B` / `0x108D` answer Success 0 only when one of the two `tMarriage`
  rows does not point at the other, or on a DB error. No status check, so normal requests succeed.
- **Z07 §2 free stats (0x10D1):** `usp_Character_setStatPoint(charNo, nMaxStat, 5 stats, itemId, lot option type,
  Σ DecItemInfo.count)`; the procedure itself consumes restat items by item ID in inventory order (the `itemKey`s the
  zone sends only reach the GameLog). `nErrorType`: 0xAC1 ok, 0xAC2 over max, 0x1097 decrease ≠ item count, 0x1096
  lowering a stack failed, 0x1094 deleting an item failed, 0xAC6 too few restat items, 0xAC4 DB. Several DB results
  return **no** 0x10D2 (D02-B10): the zone's free-stat lock then stays set. Full procedure source (rejoined by `bak.py`
  since D02): with one item to consume and none in the inventory, the stats are still lowered (D02-B20).
- **W01 §6.3 blob table:** the 2016 Character server never sends 0x100F, 0x1011, 0x1013–0x1016, 0x1018. `0x1006` codes
  except 0x591/0x5A2/0x5A3/0x31EA are written at +4 while the WM reads +2 (D02-B6).
- **W01 0x1097:** the `isGuildAcademyMember` byte is never written (stale).
- **0x1036/0x1037:** they do not save position or money. Position, level, stats are saved only by dept-16 messages from
  the zone; 0x1036 adds 1 friend point to every friend on the first login of a day (→ `0x541C` to the WM).
- **0xA004 promotion reward:** the reward table is never loaded in 2016, so no items are ever given.

## Corrections / additions for other items

- W01 §6.2 `0x107F`: the 12 u16 are 6 pairs `{u16 itemId, u16 totalLot}` (HairShop01–05, UniChange01), PDB
  `STYLE_ITEM_COUNTS[6]`.
- W01 §6.1 AVATAR `delinfo.year` (+0x27) = year − 2000 (written as `(u8)(year + 0x30)`); `CharIDChangeData` defaults to
  `{0, 0x64, 0}` when the account has no rename right.
- `0xB411` is the DB request `NC_USER_CONNECTION_DB_CHANGE_CHAR_ID_ITEM_USE_REQ` by its PDB struct (0x26 bytes + attr
  data); handlers.json's "…ITEM_USE_ACK" name is the REQ+1 guess. `0xB40A` = `NC_USER_CONNECTION_DB_CHANGE_CHAR_ID_REQ`
  by struct.
- `bak.py` now rejoins procedure source longer than one page (LOB fragments) and reads Latin-1 comments: 34 procedures
  in Character.bak / w00_Character.bak got longer, e.g. `p_Item_Upgrade_CelllInAll`, `usp_Dice_*`, `usp_Gamble_*`,
  `p_Guild_Member_SetGrade`, `usp_GuildAcademy_withdrawMoney`, `usp_Item_setPutOnBelongedCancel` (D03 / D04 areas).
- `usp_CharacterLoading` takes 11 parameters in 2016 (the backups' version has 6); `usp_CharacterLoadingDetailInfo` stores
  per-error `{u16, u32}` entries.
