# X03: Server topology: worlds, WorldManagers, zones and deployment

Cross-cutting note assembled from the shipped 2016 config files and the Login/WM/Zone exports. It is a
knowledge-base note, not a `make_plans.py` work item. It answers two practical questions:

- what a client-visible "server" is, which processes are global and which are per-world, and what has to be
  duplicated to add a second one;
- how zones are identified, how maps are assigned to them, and what `MHBasic` / `Fiesta = 99` means.

Evidence levels follow `AGENTS.md`; `(inferred)` marks deductions, everything else is read from the config or code.

## 1. Process roles

| Process | ServerInfo type | Scope | Role |
|---|---|---|---|
| Login | 4 | one for the whole service | client login, version check, world list, world-select ticket; routes `0x0C0D` to the selected WM |
| Account DB | 0 | one for the whole service | account rows, login/password, block/auth flags |
| AccountLog DB | 1 | one for the whole service | login/world-select/logout records, IP block history |
| WorldManager (WM) | 5 | **one per world** | character select, WM-owned social state (party, guild, friends, KQ, character cache), zone routing |
| Zone | 6 | many per world | one map-server process; loads a subset of the world's maps |
| Character DB | 2 | **one per world** | characters, items, friends, guild rows for that world |
| GameLog DB | 3 | **one per world** | game-log records for that world; its log path includes `World<n>` |
| OPTool | 8 | optional / can span worlds | operator connections to Login/WM/Zone |

A client-visible "server" in the login list is a **world**, and a world is exactly one **WM** plus its zones.
Adding zones does not add a server-list entry; adding a WM does.

Two WMs are two separate communities: party, raid, guild, friends, KQ state and the character cache live in the
WM (`docs/knowledge/W02.md`, `W03.md`, `W01.md`). Players on different worlds cannot party or guild together.
Adding zones under the same WM keeps one community and adds map/process capacity.

## 2. How Login sees multiple worlds

- The world list is built from the `WORLD_NAME` rows in `9Data/ServerInfo/ServerInfo.txt` (`FUN_00409eb0`).
  `0x0C0A` / `0x0C1C` send `u8 count; WORLD[count]`, where `WORLD` is 18 bytes:
  `u8 world_no; char name[16]; u8 status` (`docs/protocol/packets-login.md`).
- Login keeps a `WorldManagerSession[]` indexed by world number (`docs/pseudocode/login-server.md` §1).
  A WM announces itself with `0x0802 {echo, server_id_to = 4, server_id_from = 5, world, zone, key}`; Login
  validates it and binds the session to that world (`FUN_00408170`). The world number is the index.
- `0x0C0B NC_USER_WORLDSELECT_REQ {u8 world_no}` sends `0x0C0D` to `WM[worldNo]` and receives the WM's
  `0x0C0E`; Login replies `0x0C0C {u8 status; char wm_ip[16]; u16 wm_port; u16 validate[32]}`. The client then
  connects to that WM address (`docs/pseudocode/login-server.md` §4, §5.3).
- The WORLD status is set when the WM registers (WORLD is selectable only at status ≥ 5). The WM sends
  `0x0808 {u16 currentUsers, u16 maxUsers}` immediately and every 30 s; Login derives/updates the status and
  broadcasts `0x0C1C` on the first update (`FUN_00408580`, `FUN_00438d10`).
- A `WORLD_NAME` entry with no WM is visible but unselectable. A WM with no matching `WORLD_NAME` has nowhere
  to report its status.

## 3. Which services are shared and which are per-world

The WM's `LoadServerInfo` (`FUN_00403e70`; summarised in `docs/pseudocode/wm/W01-core.md` §2) looks up its peer
rows by `(type, world, zone, peerType)`:

```text
accountLog (1, 0, 0)          account (0, 0, 0)
character  (2, myWorld, 0)    gameLog (3, myWorld, 0)
login      (4, 0, 0, from = myType = 5)
zone listen     (myType = 5, myWorld, 0, 6)
client listen   (myType = 5, myWorld, 0, 20)
OPTool listen   (myType = 5, myWorld, 0, 8)
```

Consequences:

| Service | Identity row | Shared across worlds? |
|---|---|---|
| Login | type 4, world 0 | **yes**, one process |
| Account DB | type 0, world 0, zone 0 | **yes**, one process |
| AccountLog DB | type 1, world 0, zone 0 | **yes**, one process |
| Character DB | type 2, **world = WM's world**, zone 0 | **no**, one per world |
| GameLog DB | type 3, **world = WM's world**, zone 0 | **no**, one per world |
| WM | type 5, **world = own world**, zone 0 | **no**, one per world |
| Zone | type 6, **world = own world**, **zone = own zone** | **no**, one process per zone |

Account and AccountLog handshakes do not check the peer's world (`docs/knowledge/D01.md`), which is why one
process can serve all worlds. The WM and zones still need world-specific Character/GameLog rows; the original
layout names them `w00_Character` / `w00_GameLog`, `w01_Character` / `w01_GameLog`, etc. You can configure the
world-1 rows to point at the world-0 process, but then characters and logs are shared across worlds; the
intended layout is one per world.

Zones also connect directly to the Character DB and GameLog DB (`docs/pseudocode/zone/Z01-core.md` §1, §3.3),
so every zone of world 1 needs the world-1 Character/GameLog endpoints too.

## 4. Config files and row format

### 4.1 `9Data/ServerInfo/ServerInfo.txt`

The `SERVER_INFO` define has 9 columns:

```text
pName, nServerID, nWorldNo, nZoneNo, nServerIDFrom, pIP, nPort, nBackLog, nMaxAccept
```

- `nServerID` is the process type: 0 Account, 1 AccountLog, 2 Character, 3 GameLog, 4 Login, 5 WM, 6 Zone,
  8 OPTool, 20 client listener.
- `nServerIDFrom` is the peer type for a listener row (20 = clients, 6 = zones, 8 = OPTool). For DB rows it is 0.
- `nMaxAccept` is the listener's connection cap.

Shipped world 0 examples:

```text
SERVER_INFO "PG_Login",   4, 0, 0, 20, "0.0.0.0",   9010, 100, 200    # clients -> Login
SERVER_INFO "PG_Login",   4, 0, 0,  5, "0.0.0.0",   9011, 100, 50     # WMs -> Login
SERVER_INFO "PG_Login",   4, 0, 0,  8, "127.0.0.1", 9015,   1, 30     # OPTool

SERVER_INFO "PG_W00_WM",  5, 0, 0, 20, "0.0.0.0",   9110, 100, 2500   # clients -> WM
SERVER_INFO "PG_W00_WM",  5, 0, 0,  6, "0.0.0.0",   9111, 100, 100    # zones -> WM
SERVER_INFO "PG_W00_WM",  5, 0, 0,  8, "127.0.0.1", 9115, 100, 30     # OPTool

SERVER_INFO "PG_W00_Z00", 6, 0, 0, 20, "0.0.0.0",   9210, 100, 1700   # clients -> Zone
SERVER_INFO "PG_W00_Z00", 6, 0, 0,  6, "0.0.0.0",   9218,   1, 30     # zone ring -> Zone
SERVER_INFO "PG_W00_Z00", 6, 0, 0,  8, "127.0.0.1", 9211, 100, 30     # OPTool

SERVER_INFO "PG_AccDB",   0, 0, 0,  0, "0.0.0.0",   9000, 100, 100
SERVER_INFO "PG_ALDB",    1, 0, 0,  0, "0.0.0.0",   9311, 100, 100
SERVER_INFO "PG_W00_CDB", 2, 0, 0,  0, "0.0.0.0",   9411, 100, 100
SERVER_INFO "PG_W00_GLDB",3, 0, 0,  0, "0.0.0.0",   9511, 100, 100
```

`ODBC_INFO` has 5 columns: `pName, nType, nWorldNo, connectionString, options`. The shipped rows name the
types: 10 = Character DB and 11 = GameLog DB *(inferred from the row names)*, with world number 0 in the w00 set:

```text
ODBC_INFO "w00_Character", 10, 0, "Driver=...;Database=w00_Character", "SET LOCK_TIMEOUT 5000;"
ODBC_INFO "w00_GameLog",   11, 0, "Driver=...;Database=w00_GameLog",   "SET LOCK_TIMEOUT 5000;"
```

### 4.2 Per-process `MY_SERVER`

Each process directory has a `*ServerInfo.txt` with a `MY_SERVER` define and an include of the shared file:

```text
# WMServerInfo.txt
MY_SERVER "PG_W00_WM", "_2015_WorldManager", 5, 0, 0
#INCLUDE "../9Data/ServerInfo/ServerInfo.txt"

# w00_Zone00/ZoneServerInfo/ZoneServerInfo.txt
MY_SERVER "PG_W00_Z00", "_2015_Zone00", 6, 0, 0
#INCLUDE "../../9Data/ServerInfo/ServerInfo.txt"

# w00_Character/DataServerInfo_Character.txt
MY_SERVER "PG_W00_CDB", "_2015_Character", 2, 0, 0
#INCLUDE "../9Data/ServerInfo/ServerInfo.txt"

# w00_GameLog/DataServerInfo_GameLog.txt
MY_SERVER "PG_W00_GLDB", "_2015_GameLog", 3, 0, 0
#INCLUDE "../9Data/ServerInfo/ServerInfo.txt"
```

The last three numbers are **server type, world number, zone number**. The first string is the process name
used in its own config and logs; the row lookup itself is by type/world/zone/peer type, so keep the name unique
for clarity. The second string is a service/log name.

## 5. Zone configuration: identity, listeners, peers, maps

A Zone is configured in three places.

### 5.1 Identity

`ZoneServerInfo/ZoneServerInfo.txt` gives `MY_SERVER ... 6, world, zone`. `zs_start` parses it, stores the row,
and later reads the zone's own `SERVER_INFO` row (`FUN_0064d130`, `FUN_005a9920`). The zone number is the key
used for the zone ring and for map ownership.

### 5.2 Listeners and peers

From `ServerInfo.txt` the zone opens:

- type 6 / own world / own zone / peer 20: client listener (the address the WM gives clients in `0x1003`);
- type 6 / own world / own zone / peer 6: zone-ring listener (the previous zone connects here);
- type 6 / own world / own zone / peer 8: OPTool listener.

It finds the WM by type 5 / same world / peer 6, the Character DB by type 2 / same world, and GameLog by type 3 /
same world (`docs/pseudocode/zone/Z01-core.md` §1, §3.3). A zone's `0x0802` handshake carries its world and zone;
the WM validates the source IP against the type-6 / `listen 6` row (`W01-core.md` §7.1).

### 5.3 Map assignment: `World/Field.txt`

The map set is **not** listed in `ZoneServerInfo.txt`. It comes from the data table:

- `9Data/ServerInfo/_ServerGroup.txt` contains one word, shipped as `Fiesta`. That word is the **column name**
  in the `FieldList` table that holds the map's machine/zone number.
- `FieldContainer::fc_Load` (`FUN_004655f0`) first tries `World/<worldName>/Field.txt`, where `worldName` is
  the `WORLD_NAME` string for the zone's world (shipped `INITIO`), then falls back to `World/Field.txt`.
  This is how different worlds can use different map splits while sharing the rest of `9Data`.
- For each `FieldList` row, `FieldOption::fo_GetMechineNumber` (`FUN_0063e200`) reads the server-group column
  (e.g. `Fiesta`). Values are machine/zone numbers 0..11, plus the special 99 described in §6.
- `FieldContainer::fc_MakeField` (`FUN_004650a0`) looks up `SERVER_INFO(type 6, world, machine, listen 6)`,
  stores that zone's IP/port in `ZoneIPContainer`, inserts map → serial in the field-serial tree, and only
  calls `FieldMap::fm_Init` when `machine == myZoneNo`. So **each zone loads only its assigned maps**, but all
  zones learn the ring address of every machine number used by the table when that machine's type-6 / `listen 6`
  row exists.
- After the WM handshake, the zone sends `0x180F` with the map list it loaded; the WM stores map → zone
  (`g_Zones.AddMap`). `0x1001` character login is routed by `loginMap`; `0x1003` returns the zone's type-6 /
  `listen 20` address. A map assigned to a zone that is not running is not registered, and the WM's map-login
  path fails with `0x1002` / `0x0145`.

Shipped world-0 distribution in `World/Field.txt` (`FieldList` records only):

| `Fiesta` value | Zone | Maps | Client / ring ports |
|---|---|---|---|
| 0 | `w00_Zone00` | 36 | 9210 / 9218 |
| 1 | `w00_Zone01` | 33 | 9212 / 9219 |
| 2 | `w00_Zone02` | 45 | 9214 / 9220 |
| 3 | `w00_Zone03` | 38 | 9216 / 9221 |
| 99 | per-zone special (`MHBasic`) | 1 | §6 |

The `InstanceDungeon` table in the same file has its own `ZoneNumber` column: a zone accepts an instance-dungeon
request only when `row.zone == own zone`, and the WM/ring routes the player to the hosting zone
(`docs/pseudocode/zone/Z08-content.md` §5.3).

### 5.4 Zone ring limits

`ZoneIPContainer::zipc_Store` (`FUN_005a9640`) has 12 slots; values 0..11 are valid and anything larger trips an
assert. `zipc_GetNextZoneNo` (`FUN_005a96b0`) returns `zoneNo + 1` only when that slot has an address, otherwise
it wraps to 0. `zipc_Mechine2IP` (`FUN_005a9760`) also maps machine 99 to the zone's own number.

Therefore:

- use contiguous zone numbers `0..N-1`; a gap breaks the ring (`0 -> 2` is not followed);
- maximum 12 zones per world;
- a zone with no maps assigned to it gets no ring address and is effectively unreachable.

## 6. `MHBasic` and `Fiesta = 99`

### 6.1 What the map is

`MHBasic` is the **mini-house / estate basic room** (player housing interior), not an open-world field.

- `World/Field.txt` `FieldList` row: `MapIDClient = MHBasic`, `MapName = basic#room`, `Serial = 91`,
  `KQ = 2`, `SystemMap = 1`, `SubFrom = 0`, `SubTo = 3`, `Fiesta = 99`.
- `MapInfo.shn` row 70: `MapName = MHBasic`, `Name = Estate`, `MapFolderName = MHBasic`, `InSide = 1`,
  `KingdomMap = 2`.
- In `FieldMap::fm_Init` (`FUN_00464bc0`), `KingdomQuestMap == 2` selects the mini-house broadcast functions
  (`so_AllInMapMiniHouse`, `so_AllOfRangeMiniHouse`). The MapInfo row is looked up by the FieldList
  `mapidclient` (`MHBasic`), while `fm_MapID` is set to the sub-map name passed to `fm_Init`.

### 6.2 What 99 means

99 is a **sentinel meaning "local / this zone"**, not a literal zone number. It is outside the 0..11
machine table and does not need a `SERVER_INFO` type-6 / zone-99 row.

Three code paths agree:

1. `zipc_Mechine2IP` maps machine `0x63` (99) to the caller's own `nZoneNo`.
2. `so_LinkTo` maps `destZone == 99` to `myZone`, so a link to the mini-house does not transfer to another
   zone process (`docs/pseudocode/zone/Z01-core.md` §7.1).
3. `FieldContainer::fc_Load` has a special `uVar16 == 99` branch. Because `MHBasic` has `SubFrom = 0` and
   `SubTo = 3`, it expands the entry into internal sub-map names ending in 0..3. Each zone selects the copy
   whose suffix matches its own `nZoneNo`, then calls `fc_MakeField` with machine number = that zone number
   (not 99). *(inferred: the generated names are `MHBasic0`..`MHBasic3`; the code's last-character check is
   plain, the exact string construction is inside `MapSubString`.)*

Result with four zones:

| Zone | Loaded sub-map | Machine number used |
|---|---|---|
| 0 | `MHBasic0` | 0 |
| 1 | `MHBasic1` | 1 |
| 2 | `MHBasic2` | 2 |
| 3 | `MHBasic3` | 3 |

The single `MHBasic` `MapInfo` row supplies the assets/MapInfo for all four; the sub-map name is the server-side
`fm_MapID`. This gives every zone a local mini-house interior, so entering a house never crosses the zone ring.

### 6.3 Practical consequences

- If you add zone `n`, extend `MHBasic`'s `SubTo` to at least `n`, or `MHBasic<n>` is never generated and the
  mini-house interior is unavailable on that zone.
- The special branch parses only the **last character** of the sub-map name (`lastChar - '0'`). Zones 0–9 work;
  zone 10 would look like suffix `0` and collide with zone 0. The ring allows 12 zones, but this particular
  mechanism is single-digit.
- Do not replace `99` with a normal zone number casually. The `99` branch is what filters the sub-map copies
  to the local zone. With a value such as `0`, `fc_Load` takes the non-99 `else` path and calls `fc_MakeField`
  for all generated `MHBasic0..3` with machine 0: only zone 0 loads them (four map IDs on one zone), and zones
  1+ get none. Use `99` plus `SubFrom`/`SubTo` for the per-zone layout.
- 99 consumes no ring slot and is not included in the `zipc_Store` 0..11 limit.

## 7. Adding a second world: checklist

Using world 0 as the template; replace names/ports/IPs as needed.

1. **Add the world-list entry** to `9Data/ServerInfo/ServerInfo.txt`:

   ```text
   WORLD_NAME 1, "WORLD2", "../9Data/Shine"
   ```

2. **Add the world-1 WM rows** (`type 5`, world 1, zone 0). Use unique ports if sharing a host. The
   `listen 20` `pIP` and `nPort` are copied into `0x0C0C`, so the IP must be reachable by the client (not
   `0.0.0.0` for a remote client):

   ```text
   SERVER_INFO "PG_W01_WM", 5, 1, 0, 20, "<reachable-ip>", 19110, 100, 2500
   SERVER_INFO "PG_W01_WM", 5, 1, 0,  6, "<reachable-ip>", 19111, 100, 100
   SERVER_INFO "PG_W01_WM", 5, 1, 0,  8, "127.0.0.1",    19115, 100, 30
   ```

3. **Add world-1 zone rows** (`type 6`, world 1, zone `n`), one client/ring/OPTool row per zone; see §5.2.

4. **Add world-1 Character and GameLog rows** (`type 2` / `type 3`, world 1, zone 0) with unique ports:

   ```text
   SERVER_INFO "PG_W01_CDB",  2, 1, 0, 0, "<ip>", 19411, 100, 100
   SERVER_INFO "PG_W01_GLDB", 3, 1, 0, 0, "<ip>", 19511, 100, 100
   ```

   Add matching `ODBC_INFO` rows with types 10/11, world 1, and the new database names, e.g.
   `w01_Character` and `w01_GameLog`. Create/clone those databases.

5. **Copy the process directories** and update each `MY_SERVER`:

   ```text
   w01_WorldManager/WMServerInfo.txt          -> 5, 1, 0
   w01_Zone00/ZoneServerInfo/ZoneServerInfo.txt -> 6, 1, 0
   w01_Zone01/...                             -> 6, 1, 1
   w01_Character/DataServerInfo_Character.txt -> 2, 1, 0
   w01_GameLog/DataServerInfo_GameLog.txt     -> 3, 1, 0
   ```

   The `#INCLUDE ../9Data/ServerInfo/ServerInfo.txt` paths can stay shared.

6. **Keep Login, Account and AccountLog at world 0.** Their rows are looked up as `(4,0,0)`, `(0,0,0)`,
   `(1,0,0)` by both Login and WM.

7. **Start order:** Account/AccountLog and the world-1 Character/GameLog DBs, then Login, then the world-1 WM,
   then its zones. Login loads `ServerInfo.txt` at startup, so restart it after editing. The world-1 entry
   starts at status 0 (or 2 if its type-5 row is missing), which is unselectable; WM registration sets a
   selectable status, and its first `0x0808` supplies the user counts.

8. **Map split:** the common `World/Field.txt` assigns maps to zones 0..3 regardless of world. Either run
   world-1 zones 0..3 too, or create `World/<worldName>/Field.txt` for world 1 with a different
   `Fiesta` column (for example all maps assigned to 0 for a single-zone world).

## 8. Adding or reducing zones within a world

- **Add zone `n`:** add `SERVER_INFO` type-6 rows, copy a zone directory with `MY_SERVER 6, world, n`, and move
  some map rows' server-group value (`Fiesta`) to `n`. Keep `n` contiguous with the existing zones. Restart the
  zones (they read `Field.txt` at startup); the WM can stay up and learns the new zone's maps from `0x180F`.
  Restart the WM too if you changed its own `SERVER_INFO` rows.
- **Run one zone:** set every `FieldList` row's server-group value to 0, or use a per-world
  `World/<worldName>/Field.txt` override. This works, but the single process loads all 153 open-world maps,
  its client listener's `nMaxAccept` (1700 in the shipped config) caps the world, and the zone ring has only
  itself.
- **Do not** run two zones with the same zone number; the WM keys `g_Zones` by zone number and the ring stores
  one address per machine.
- **Do not** assign the same map to two zones. `Zones_FindByMap` uses the first active map registration.

## 9. Open points / caveats

- The exact `MHBasic<n>` string construction is `(inferred)` from `MapSubString` plus the last-character check;
  the important behaviour — one local copy per zone, machine number = zone number — is plain in `fc_Load`.
- Whether the client ever sees the internal `MHBasic<n>` name or only the MapInfo index is not traced here;
  `fm_Init` uses the FieldList `mapidclient` for MapInfo and the sub-map name for `fm_MapID`.
- The 12-zone ring limit and the single-digit `MHBasic` suffix logic conflict for zones 10–11; a rebuild would
  need a different naming scheme if it wants that many zones with local mini-houses.
- The `WORLD_NAME` third field (`../9Data/Shine`) appears to be the world data path *(inferred)*; this note
  does not trace how the certification/start scripts use it.
