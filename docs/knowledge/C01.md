# C01: Client packet-handler inventory (Fiesta.bin 2016)

Every packet the 2016 client accepts, which client function handles it, and what the client does with it.
Machine-readable: [`re-data/client-handlers.json`](../../re-data/client-handlers.json), produced by
`python3 -I tools/protocol-re/client_handlers.py .` (hand summaries live in `tools/protocol-re/client_summaries.py`).
`catalog.py` merges it into `docs/protocol/opcodes.json` (field `client`, and names with `name_source: client`).

## 1. Receive path

```pseudo
PgNet.RecvLoop(scene, maxPackets):                       client @ FUN_008c7b60 (PgNet / Net vtable slot 4)
  for each complete packet {u16 opcode, payload}:
    dept = opcode >> 10 ; cmd = opcode & 0x3ff
    if not Net.PreDispatch(dept, cmd, size, payload):     @ FUN_006d2fa0 (Net vtable slot 6)
        scene.OnPacket(dept, cmd, size, payload)          PgFrameWork vtable slot 13 (+0x34)

Net.PreDispatch:                                         @ FUN_006d2fa0, runs in every scene
  0x0804 heartbeat   -> if enabled reply 0x0805 (empty); return handled
  0x080E server time -> {u8 h, u8 m, u8 s} into the clock object; return handled
  0x0819             -> return handled (no action)
  anything else      -> not handled

GameFrameWork.OnPacket(dept, cmd, size, payload):        @ FUN_004be490 (GameFrameWork::ProcessNetMsg)
  ITask::ProcessNetMsgAll(dept, cmd, size, payload)      @ FUN_006a2030 -> ITask::ProcessNetMsg FUN_006a1fd0:
      every live ITask (tree rooted at PTR_vftable_00a6c110) gets vtable slot 4 (+0x10)(dept, cmd, size, payload)
  switch dept: switch cmd: handler(this, size, payload)  (624 opcodes, then 27 ITask classes add more)
```

The dispatcher signature is `__thiscall OnPacket(int dept, int cmd, int size, void *payload)`; handlers
usually return `size`. Unknown opcodes are dropped silently (no error, no disconnect).
Only one scene object is current at a time, so **a packet is accepted only by the scene that is active**
(e.g. `0x1003` only in character select, `0x1802` only while logging into a zone or changing map).

Total: 900 distinct opcodes handled. The functions carry their official 2017 names *(pdb2017)* in
`tools/protocol-re/names/client/C01.json` (C02 follow-up; the former C01 names in brackets): scene dispatchers =
`<FrameWork>::ProcessNetMsg` (`<Class>_OnPacket`), ITask handlers = `<Task>::OnProcessNetMsg` (`<Task>_OnPacket`),
`PgNet::DispatchMsg` (`PgNet_RecvLoop`), `ITask::ProcessNetMsg` / `ITask::ProcessNetMsgAll` (`ITask_DispatchTree` /
`ITask_BroadcastPacket`), `PgFrameWork::ProcessNetMsg` (`PgFrameWork_OnPacket_None`), `ErrMsgTable::GetErrMsg`
(`ErrorText`), `TextData::Get` / `TextData2::Get` (`GetText` / `GetText2`), `AccountFrameWork::NcUserVersionReq`
(`Login_SendVersion`), `LoginWorldNetFrameWork::NcUserLoginWorldReq` (`WmLogin_SendLoginReq`),
`ZoneLoginNetFrameWork::NcMapLoginReq` (`ZoneLogin_SendMapLoginReq`). 34 of them are byte/opcode matches by
`pdb_port.py`; the other 14 (`GameFrameWork`, `LoginWorldNetFrameWork`, `CHairShopFrameWork`, `GatheringTask`,
`GuildJoinReqTask`, `ChargedItemUseTask`, `GuildMemberGradeSetupTask`, `ItemRepairTask`, `GuildMemberTask`, `GuildTask`,
`GuildAcademyMasterAppointTask`, `GuildAcademyMasterInitializeTask`, and `Net::ProcessNetMsg` for `Net_PreDispatch`)
are the 2017 method of the same RTTI class in the same vtable role *(inferred)*.

Ruled out: `FUN_004aaa40`, `FUN_00665920`, `FUN_00666ce0`, `FUN_00546270`, `FUN_00515010` (the plan's
candidates) split a **cell id** with `>> 10` / `& 0x3ff` (inventory type, slot), not an opcode. `FUN_004aaa40` is the
handler of `0x3001` (item cell change). A scan of every client function shaped like `f(dept, cmd, size, payload)`
(and of all RTTI vtables, including secondary ones from multiple inheritance) found no other packet receiver.

**Byte-table switch (GuildTask).** `GuildTask::OnProcessNetMsg` (`FUN_006b7e70`) handles dept 0x1d (guild, guild war,
guild tournament, guild storage/emblem) with an MSVC two-level switch Ghidra could not normalize
("Could not find normalized switch variable"):

```pseudo
@ FUN_006b7e70 (case dept 0x1d), machine code 0x6b811c..0x6b8131
  if cmd - 6 > 0x105: break                          // cmd 6..0x10b
  idx = byte[0x6b8e20 + (cmd - 6)]                   // = byte[0x6b8e1a + cmd]
  goto jumptable[0x6b8d0c + 4*idx]                   // idx 0x44 = default (194 cmds), 68 real cases
```

The decompiled text shows `switch(*(undefined1 *)((int)&PTR_caseD_43_006b8e18 + param_2 + 2))` with `case idx:`
labels. `client_handlers.py` resolves those labels to cmd values by reading the byte table from `Fiesta.bin`.
Check: every opcode in the table that already had a server-side name lands on a handler whose texts match
(0x749d RECALL_ENTER_ACK -> "Entry Time is Over", 0x74d4 DICEGAME_THROW_ACK -> dice texts, 0x74fe
HISTORY_LIST_ACK -> guild information). Of the 37 functions the walker visits, this is the only one with a
jump-table warning. Many of these guild handlers call a listener object in `this+0x40` through its vtable
(slots +0..+0x44) with the payload, so their summaries show the payload passed on rather than read.

## 4. Per-scene handlers (pre-game scenes checked by hand)

Opcode names are the catalog's (`opcodes.json`; mostly `pdb2017`, C02). **`Client handler` is not always the scene's
`On_NC_*` method:** for some opcodes 2016 inlined the thin 2017 `Scene::On_NC_*` wrapper, so the function listed (and the
`func` of `client-handlers.json`) is a helper it calls. One helper can then serve several opcodes, e.g. `FUN_00479fa0`
(show error text) for 13 failure ACKs, `FUN_0049feb0` for both NC_MAP_LINKSAME_CMD and NC_CHAR_REVIVESAME_CMD; the
16 such functions and the 52 opcodes whose handler size differs from the 2017 method are listed in C02 §8
("Folded handlers", `pdb_port.py -v`). Use the 2017 method of the same name (`client2017` export) as the readable
reference for those.

GameFrameWork handlers and ITask handlers carry `(auto)` summaries in the JSON: payload offsets read (`fields`,
heuristic: direct reads in the handler and in callees that receive the payload pointer, up to depth 2), client
texts the handler can show (`texts`, from TextData*.shn), and literal strings referenced. Items that document a
zone/WM handler should replace these with real summaries in `client_summaries.py` (append-only by opcode key).

Every JSON entry also has `senders`: the server functions that send the opcode (`layouts.json` s2c sites) under
their names from `tools/protocol-re/names/<srv>/` (zone: Z01's original profiler names such as
`ShinePlayer_so_charskilldata`; WM: W01). The `(auto)` summaries quote the named ones ("sent by: …"). These are
function names, not opcode names, so they are not fed into `opcodes.json` names.

## 6. Not reconstructed / uncertain

- `fields` in the JSON are heuristic (pattern match on the decompiled text). Offsets inside loops over variable
  records are reported as the first record's offsets. Names are null unless a summary gives them.
- 108 game-scene handlers report no payload read: the handler takes the payload under a cast the extractor does not
  follow, or works only on `this`.
- `0x7c07`, `0x9010`, `0x103c`, `0x1047`, `0x1049`, `0x10de` are still described by shape only (no named zone/WM
  sender). The other zone-login data packets are identified through Z01's sender names; their record layouts belong
  to the zone items (Z07: character blobs).
- `0x083a` (WM) sends to both clients and a zone in one function; which send carries 0x083a was not settled.
- ITask instances are created at runtime; which tasks exist at a given moment (and so whether e.g. `0x740a` is
  accepted outside a guild UI) was not traced.
