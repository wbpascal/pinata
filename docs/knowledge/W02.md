## Facts other items need

- **The WM owns parties and raids; nothing is stored in a database.** A party/raid survives its members' logout
  (members stay in it offline) but not a WM restart. Zones are only notified; they ask with 0x384E for a member list
  and can force a join (0x3860) or a leave (0x3861).
- **Every party/raid notification to zones is broadcast to all zones** (not only the members' zones). Zone items
  (party manager in the zone) must filter by partyNo / raidNo / charNo themselves.
- **partyNo** = party slot index 0..3999, **raidNo** = raid slot index 0..499. Session `+0x639 u16 partyNo`,
  `+0x63b u16 raidNo` (0xFFFF = none), sent to zones in 0x1030 (W01). On map login the WM re-derives partyNo /
  raidNo from the registries and refreshes the member's handles (wm/zone handle, zoneNo, level) in the party record.
- PARTY_MEMBER (0x24) = `PROTO_PARTY_MEMBER_AND_ZONEMERCHINE` (0x20: chrregnum, zonecharhandle, wmcharhandle,
  charname[20], level, flag, charclass, ZoneMerchineNo) + 4 unused bytes. `flag` bit 0 = invited and not accepted
  yet; such members are excluded from member lists, member counts sent to zones, and broadcasts.
- Loot rule block (party +0xb8, raid +0x24): `u32 lootType[4]` per item grade (0 regular, 1 named, 2 rare/set,
  3 unique) with type 0 free-for-all, 1 alternating, 2 designated looter, 3 dice; `u32 looterCharNo`. Setting
  `{grade g, type t}` gives grades ≥ g the type t and resets grades < g to 0 (FUN_004646f0). Zones get it in 0x384D
  (party) / 0xB00B (raid) and the looter in 0x385E / 0xB03E.
- **A raid = 4 parties** (party slots flagged `reservedForRaid` at +0xcd). Raid members are real members of those
  parties; zone party logic for raid members therefore sees 4 parties. Positions are `{nPartyIndex 0..3, nSlotIndex 0..4}`.
  Creating a raid (0xB001) turns the creator's party into `partyNo[0]` and reserves 3 empty party slots.
- `Client_IsInRaid` (FUN_00431240) gates all party actions: a raid member cannot invite, kick, change loot, or
  leave the party with dept-14 requests.
- Map registration (0x180F NC_MAP_REGIST_CMD) byte `canparty`: 0 forbids party/raid invitations on that map,
  **2 = guild-only** (both characters must be in the same guild); `IsPartyReleaseMap` makes a character leave its
  party/raid when it enters the map (the 0x180C payload byte +0x2e = 1 does the same).
- "Opposite team" (0x4DA / 0x1ED4) = kingdom-quest teams via `g_InstanceMaps` (FUN_00433740, log text "Kingdom Quest Team").
- Party level-gap check exists (error 0x4D1) but uses a limit of 1000 levels, so it never fails in 2016.
- Session `+0x1ecd0` = pending raid invitation (raidNo). Session `+0x1ecd4` = loggingOut: 1 while 0x0C18
  NC_USER_NORMALLOGOUT_CMD runs CharacterLogout (FUN_00412df0), so the leaver is not counted as an online raid member.
- The single-option blob (+0x658, W01 §6.3) is `PROTO_NC_CHAR_SINGLE_OPTION_CMD` *(pdb2017)*: +0 chrregnum, +4 resttime,
  +8 autopick, +9 mystery_vault, **+10 u32 nChatBan**, +14 bFirstJoin. A chat-banned character's raid chat is echoed
  to itself only (a "shadow" mute).
- Friends are told about party state with 0x540E NC_FRIEND_PARTY_CMD `{name[20], u8 inParty}` (FUN_00435ee0) — W04.
- **Original-server bugs** (W02-B1 … W02-B12, each also tagged `(original bug)` inline) are listed in one table in W02-party-raid.md §9 with the 2016 behaviour and the
  likely intent, so a rebuild can choose to reproduce or fix each one. Main ones: 0x385A errors sent as opcode 0xB05B,
  raid chat refusal 0x1FC1 vs client 0x1FC2, raid loot rule changeable by any member, raid-full returns success.
- CParserZone 0x6009 (dept 24 NC_CT, FUN_0042cda0) forwards `0x380A {u32 charNo, u16}` to the character's zone;
  it is in W04's scope table.
