## 2. Facts found on the way

- **`0x10D2` single-option block (CharDB → WM, 17 bytes; `annotations/P02.json` names are P02's own):**
  `usp_Character_getSingleOption` *(db-backup, `w00_Character.bak`, 2010.10.18)* selects `bMysteryBolt`,
  `bAutoPick`, `dRestExpLastExecuteTime`, `nChatBan` from `tCharacterSingleOption` and inserts the row when it is
  missing (error −3192). So `nOption1` = `bMysteryBolt`, `nOption2` = `bAutoPick`, `tTime` =
  `dRestExpLastExecuteTime`, `nOption4` = `nChatBan`. The timestamp is the last rest-exp run, not a "last save"
  time as capture-validation §7.4 inferred.
- **`0x1050 NC_CHAR_REVIVEOTHER_CMD`** cannot come from a death on a normal field: `sp_ReviveReqProcess` @
  FUN_00451bd0 links to the current map unless the map is a guild-tournament map (`fm_IsGuildTournametnMap` @
  FUN_00475770, the test Z07 §3.1 calls "revive in place map") or a KQ grants revives.
- **Scenario 39 step 2 as X02 wrote it** ("the map change (captured for the other-map case)") was wrong: the
  captured revive is `0x104F`.
- `p_Item_SetStorage` *(db-backup)* returns `@@ROWCOUNT` of one `UPDATE tItem … WHERE nItemKey`, so an equip or
  unequip is refused only when the row is missing (S18); `p_User_MoneyGet` returns 0 only when its first-access
  `INSERT INTO tUserMoney VALUES (nUserNo, 0)` fails (S19 b).
