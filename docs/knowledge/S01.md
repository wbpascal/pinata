# S01 knowledge: 2016 server PDBs (NA2016)

Facts other items need from the NA2016 set (`Files/Server/NA2016/`): the same 2016 builds as `Files/Server/2016/` plus
the private PDBs of Login, WorldManager, Zone, Account and AccountLog. Sections are added part by part (status:
`docs/plan/status/S01.md`). Evidence labels as in `AGENTS.md`; *(pdb2016)* = name or type from these PDBs.

## 1. NA2016 executables: private-server patches

### 1.1 What differs from the 2016 exes

Compared section by section with the 2016 exes (same PE timestamp, RSDS GUID/age, entry point, checksum field):

| Server | `.text` / `.rdata` / `.data` / `.rsrc` | Last section |
|---|---|---|
| Login, Account, AccountLog, Character, GameLog | identical | `.reloc` replaced by `.custom` (RWX `0xE0000040`, virtual 0x1024, raw 0x1200, **all zero**) |
| WorldManager | `.text`: 11 hook sites (§1.2) | `.custom` @ 0x00A30000: 0x130 bytes of hook code |
| Zone (Zone00–04, byte-identical) | `.text`: 2 hooks + 2 byte edits (§1.3) | `.custom` @ 0x1550F000: 0x46 bytes of hook code |

Header: only the last section header and `SizeOfImage` change. The relocation data directory still points at the old
`.reloc` RVA (now the zeroed `.custom`) and `DYNAMIC_BASE` stays set; the checksum field is not recomputed.
`.custom` lies at the same VA as the 2016 `.reloc`. To disassemble a patched exe, copy the 2016 exe, paste the NA
`.text` and the `.custom` raw bytes over `.text` / `.reloc`, and run `objdump -D --start-address=…` on the copy
(llvm-objdump rejects the NA file itself: "end of the file was unexpectedly encountered").

All hooks are `jmp <custom>` + `nop` padding over the original instructions; the hook re-executes the overwritten
instructions with an extra check and jumps back. None of the five PDBs changes (they describe the unpatched code).

**Consequence for evidence:** a capture or observation from an NA2016-based server shows the patched behaviour in the
handlers below, not the 2016 behaviour. Read the 2016 code (the `<bin>` / `<bin>-pdb` exports) for the spec.

## 2. Packet layouts and opcode names from the 2016 server PDBs

### 2.1 `docs/protocol/pdb2016-layouts.json` and where it is used

- Generated by `pdb.py <Zone.pdb> layouts2016 OUT <WorldManager.pdb> <Login.pdb> <Account.pdb> <AccountLog.pdb>`
  (`regen.sh` runs it after the 2017 `pdb-layouts.json`). Same schema as `pdb-layouts.json` (C02) plus per opcode
  `pdbs` (the PDBs whose `PROTOCOL_COMMAND_*` enums carry the value) and a top-level `disagreements` list.
- Merge rule: per opcode the first PDB in the order Zone, WorldManager, Login, Account, AccountLog that has the opcode's
  own `PROTO_<name>` struct; a struct reached only through `pdb.py`'s name alias (`_CLIENT_`/`_ZONE_` dropped,
  `struct_alias: true`) is used only if no PDB has the exact one. Alias layouts (`alts`, two enum names on one value)
  are merged over all PDBs, because each PDB only holds the types its binary uses.
- Coverage: **2705 opcodes** (union of the five PDBs' enums; Zone+WM 1489, Zone only 611, WM only 116, all five 211, …),
  **2054 with a struct** (1201 from Zone, the rest from WM/Login/Account/AccountLog), 168 element structs.
- Disagreements between the five PDBs: **none** for names, opcode values, exact structs or element structs (field
  notes differ only in how an anonymous union is named). The 3 listed in the file are alias-only: WM lacks the exact
  struct and the alias guess picks the WM↔zone variant (0x103D `PROTO_NC_CHAR_SKILL_CMD` 9 vs zone's exact
  `PROTO_NC_CHAR_CLIENT_SKILL_CMD` 10; 0x1047 ITEM_CMD 3 vs CLIENT_ITEM_CMD 3; 0x1123 MINIMON_INFO_CMD 56 vs
  `…_CLIENT_CMD` 50). The merged file uses the exact zone structs.
- Part 3 additions: 3 disagreements of kind `variants` (0x0452, 0x10AE, 0x5C05: Zone.pdb holds two definitions, §2.4)
  and inherited base-class members (§2.4).
- Header: 215 structs declare the 6-byte server-internal ref as their first member (`header`/`packheader`/
  `netpacketheader`/`netpacketzoneheader` = `NETPACKETZONEHEADER { u16 clienthandle; u32 charregistnumber }`,
  e.g. 0x5C05). Other server-internal packets that carry the ref in the 2016 code do not declare it (`docs/knowledge/Z01.md` §6).
- Consumers (rank: hand annotation > **pdb2016** > pdb2017 > generated `layouts.json`):
  - `packets.py`: "**2016 PDB layout** *(pdb2016)*" table where no annotation exists; appends "2017 client PDB
    differs: …" when the 2017 struct has another size or fields. A pdb2016 struct that is only an alias guess yields to
    an exact pdb2017 struct (only case: **0x182A** `NC_MAP_LINKEND_CLIENT_CMD`: no 2016 PDB has
    `PROTO_NC_MAP_LINKEND_CLIENT_CMD`, the alias would be the 47-byte WM↔zone `PROTO_NC_MAP_LINKEND_CMD`, but WM
    `FUN_0042d8d0` sends 1 byte = the empty 2017 struct).
  - `pcap_decode.py` (`load_docs` → `docs["pdb"][op]["src"]` = `pdb2016`/`pdb2017`, decoded field tag `(pdb2016)`)
    and `make_dissector.py` (`F.PDB[op][1].src`), same rule. Element structs: 2016 definitions win on a name clash
    (5 clash, §2.3). Both selftests check the 0x1801/0x182A/0x0830 cases.
  - `catalog.py` names (§2.2). `pdb2017` stays the source for opcodes or structs the 2016 PDBs lack.

### 2.2 Opcode names: `pdb2016` in `catalog.py`

- Rank: **pdb2016 first** (official enum name of the exact build), then the old order (C02 verdicts, client, handler,
  pdb2017, log literal, REQ+1). If the 2016 code's own name (handler profiler/log string, or a client-proven name) is
  one of the value's enum aliases, that alias is used (6 values have two enum names, e.g. 0x0830
  `NC_MISC_CONNECTFROMWHERE_DB_ACK` / `NC_MISC_SERVERPARAMETER_ACK`). Result: 2518 of 2572 catalogued opcodes are
  named `pdb2016`; `†` is no longer shown for them.
- Where the 2016 code's string names the opcode differently, `opcodes.json` keeps it as `code_name` and the
  `opcodes-*.md` Name column shows "(2016 code: …)". These are **exactly the 51 opcodes of C02's
  `pdb-name-verdicts.json`**: the 2016 enums already carry the 2017 names, so every C02 conflict was a 2016 profiler/
  log string that differs from the enum (copy-pasted or stale strings), not a 2016→2017 rename. The two verdicts
  that kept the 2016 string because "2017 renamed it" are settled the other way: **0x34CF** is
  `NC_ITEMDB_RESET_SCROLL_LINK_MAP_INFO_CMD` (code string `fc_NC_ITEMDB_MAPLINK_ITEM_COMPARE_MAP_REQ`) and **0xBC0D**
  is `NC_GAMBLE_COIN_VIPCARD_UI_OPEN_REQ` (code string `NC_GAMBLE_COIN_USE_VIPCARD_REQ`) *(pdb2016)*. Items that cite
  the code string as the opcode name: part 3 follow-up table.
- `pdb-name-verdicts.json` (C02) is now only consulted for opcodes outside the 2016 enums (none of its 51).

### 2.4 Several definitions of one type in a 2016 PDB; base-class members (part 3)

**Two definitions of one name.** A PDB keeps one type record per *distinct* definition. In the 2016 server PDBs a few
names have two different complete definitions: translation units of the same build were compiled against different
versions of a header. Until part 3, `pdb.py` used the first one only, and the first one is often the **stale** one:
