## 1. Wedding sub-status 5–8 (answers D02 §11 end / §16)

The zone does **not** mask bit 2 of `Sub` (`Status >> 4` of `0x1081`). `Checker::DivorceLimit` FUN_005a1c90 (Main 2,
run on every `0x1081` before the copy goes to the client, and once per wall-clock minute from `ShinePlayer::so_Routine`)
handles the marker values as explicit cases and clears them through `0x1082 NC_CHAR_WEDDINGDATA_CMD`
(`so_ply_WeddingInfoUpdate` FUN_0059f390):

| Sub from the DB | Zone action | Stored back |
|---|---|---|
| 5 (= 1 + 4) / 7 (= 3 + 4): own agreement / forced application cancelled (partner refused or let it expire) | refund 250 000 / 750 000 (`so_ply_IncDecMoney`, once per session: `sp_LockRefundReq`), `0x205D {0x1387}` "Your spouse refused to get a divorce." | Sub 0 |
| 6 (= 2 + 4): partner applied by agreement | `0x205D {0x1385}` "Your spouse has filed for a collaborative divorce." | Sub 2 |
| 8 (= 4 + 4): partner applied by force | none here; then `so_ply_WeddingData` sends `0x205D {0x1384}` for Sub 4 | Sub 4 |

Sub 1–4 run the expiry checks (0x108F / 0x108D); Sub 9–15 are ignored. Main 3 with any Sub ≠ 0 runs
`so_ply_DivorceProcess` FUN_0059f550 (skills erased, present destroyed, abstates 293–295 reset, Sub → 0; Sub 2 = annulment
message 0x1389). The w00 DB writes 4 (not 8) for the forced partner, so case 8 is only reached with a DB that writes 8.
The 2016 client keeps only `Status & 0xF` (Main) from `0x1081` (WeddingTask FUN_006dd280). Details: Z13 §4.4.

## 3. Wedding hall facts

- One reservation per zone (`weddinghall` DAT_0086ea38): reservation time + 20 min = guest entry and couple recall,
  + 5 min entry closes, + 10 min hall free. Checked once per wall-clock minute (`wh_Routine` from `zs_mainthreadfunction`).
- The ceremony is the scenario `ScenarioBookShelf/Wedding/Wedding.ps` (15-minute time limit); its statement
  `weddingcomplete` sends `0x1091 NC_CHAR_WEDDING_DO_REQ` when both partners are on the zone.
- Zone-ring packets: `0x2055` couple entrance (recall on other zones), `0x10AA` partner summon (skill `SummonMate01`,
  errors 0xFCE / 0xFCF in `0x2434`), `0x10AB` wedding-data refresh (annotations `docs/protocol/annotations/Z13.json`).

## 7. Mounts (output §7–§8)

- `eMoverSystemType` = `MOVER_SYSTEM_TYPE`: 0 horse, 2 mover, 3 none (`MVST_MAX`; Z07 §8's "ride kind 3 = got off").
- Z02 §9.1 `row+0xc4 / +0xc6` = `RIDING.FeedGauge` / `HGauge`.
- Z02 §2.2 reads player vt 0xd4c(1) as "force"; the argument is "only if changed" (0 = always send).
- Z07 §8 "mover script hook (+0x1f4c vt 0x40) → FUN_0055f0a0" is the item attr's `iac_GetHungry` + `smv_SendHungryInfo`
  (0xCC0A), not a script.
- Map links: the first rider to arrive rebuilds the mover with its bookings; the master's booking expires after 60 s
  (mover freed); an unbooked rider gets 0x306D; a passenger linking alone creates a one-tick phantom mover (Z13-B60) (§8.5).
- `MoverAbility.shn` / `MoverUseSkill.shn` are empty in 2016: every mover is NoDamage, mover combat and skills (0xCC0E /
  0xCC0F have no zone handler) are dead code with the 2016 data (§8.9).
- `smo_ply_SendSpeedInformation` (vt 0xeb8) has no caller for players or movers.
- Client 0xCC03 / 0xCC07 / 0xCC09 ignore the success codes 0x3068 / 0x3080 / 0x3090, so Z07's "success on the FAIL opcode"
  is by design.

## 9. Review additions (part 11)

- **How the wedding partner is chosen** (open in Z02 §10): the proposal ring's actor `UseItemPropose::uib_CanUseItem`
  FUN_00596660 takes the user's current target, runs `Checker::WhenPropose` / `WhenBeProposed` / `WhenProposeBoth` and
  writes each one's charNo into the other's `Partner.RegisterNumber` (wedding data +0x25); `uib_DirectUse` FUN_00596770
  then sends `0x204E NC_ACT_WEDDING_PROPOSE_WORD_REQ` (no payload), on which the client opens its propose-word input window.
  The pairing is never cleared (Z13-B66). Output §4.9.
- **Client task event 0x19** (2017 client, same code in the 2016 tasks): a task's `(0x19, text)` message goes up the task
  tree (`ITask::DirectDispatchToParent`) to `GameFrameWork::DirectMessage`, case 0x19 = `AddSysMsg(text)`: a system chat
  line. Tasks that report a code this way (e.g. `StatPointReqTask`'s `"err: %d"`) therefore show it in chat. Event 0x1B =
  a message-box answer (`*arg == 0`: first button).
- **0x205E `NC_ACT_WEDDING_DIVORCE_REFUSE_CMD`** is sent (no payload) by `WeddingTask::DirectMessage` FUN_006dcba0 as the
  answer to the 0x205D code 0x1384 dialog (first button); the other button sends nothing.
- `ShinePlayer::so_SaveItem_Part` FUN_00456030 (player vt 0x3b8, WM 0x4013): part marks 5 = inventory (box 9),
  8 = equipment (box 8), 0x12 = mini-house item box (box 12), 0x22 = action box (box 15). Output §2.8.
