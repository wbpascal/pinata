## 1. Wedding sub-status 5–8 (answers D02 §11 end / §16)

The zone does **not** mask bit 2 of `Sub` (`Status >> 4` of `0x1081`). `Checker::DivorceLimit` FUN_005a1c90 (Main 2,
run on every `0x1081` before the copy goes to the client, and once per wall-clock minute from `ShinePlayer::so_Routine`)
handles the marker values as explicit cases and clears them through `0x1082 NC_CHAR_WEDDINGDATA_CMD`
(`so_ply_WeddingInfoUpdate` FUN_0059f390):

| Sub from the DB | Zone action | Stored back |
|---|---|---|
| 5 (= 1 + 4) / 7 (= 3 + 4): own agreement / forced application cancelled (partner refused or let it expire) | refund 250 000 / 750 000 (`so_ply_IncDecMoney`, once per session: `sp_LockRefundReq`), `0x205D {0x1387}` "Your spouse refused to get a divorce." | Sub 0 |
| 6 (= 2 + 4): partner applied by agreement | `0x205D {0x1385}` "Your spouse has filed for a collaborative divorce." | Sub 2 |
| 8 (= 4 + 4): partner applied by force | none here; then `so_ply_WeddingData` sends `0x205D {0x1384}` for Sub 4 | Sub 4 |

Sub 1–4 run the expiry checks (0x108F / 0x108D); Sub 9–15 are ignored. Main 3 with any Sub ≠ 0 runs
`so_ply_DivorceProcess` FUN_0059f550 (skills erased, present destroyed, abstates 293–295 reset, Sub → 0; Sub 2 = annulment
message 0x1389). The w00 DB writes 4 (not 8) for the forced partner, so case 8 is only reached with a DB that writes 8.
The 2016 client keeps only `Status & 0xF` (Main) from `0x1081` (WeddingTask FUN_006dd280). Details: Z13 §4.4.

## 2. Corrections to earlier items (wedding)

- Z07 §5.1 `FUN_005a1c90` (`Checker::DivorceLimit`) "Sub 0: vt 0x40c, vt 0x418 (not traced)": these are
  `sp_UnlockRefundReq` / `sp_UnlockRefundCancelReq` (zone-only refund / cancel locks); the function also handles Sub 5–8

- Z07 §5.4 / §12 "hall timetable / `wh_Reserv` internals not reconstructed" and §5.5 `FUN_005b92a0`: Z13 §4.2–§4.3
  (`FUN_005b92a0` = `CAnnounceSystem::AnnounceSystem_ProposeAccept`, WM 0x6401 type 12).
- Z02 §10: the 0x2053 reservation has no NPC or map check, and each zone has its own `weddinghall` (Z13-B27); the
  "wedding application" item of 0x1308 is `WeddingCoupon`, consumed when the couple is recalled.

## 3. Wedding hall facts

- One reservation per zone (`weddinghall` DAT_0086ea38): reservation time + 20 min = guest entry and couple recall,
  + 5 min entry closes, + 10 min hall free. Checked once per wall-clock minute (`wh_Routine` from `zs_mainthreadfunction`).
- The ceremony is the scenario `ScenarioBookShelf/Wedding/Wedding.ps` (15-minute time limit); its statement
  `weddingcomplete` sends `0x1091 NC_CHAR_WEDDING_DO_REQ` when both partners are on the zone.
- Zone-ring packets: `0x2055` couple entrance (recall on other zones), `0x10AA` partner summon (skill `SummonMate01`,
  errors 0xFCE / 0xFCF in `0x2434`), `0x10AB` wedding-data refresh (annotations `docs/protocol/annotations/Z13.json`).
