# Z01 knowledge: zone core facts for other items

Zone binary: `Files/Server/2016/w00_Zone00/5ZoneServer2.exe`, export `re-data/exports/zone`. Pseudocode:
[`docs/pseudocode/zone/Z01-core.md`](../pseudocode/zone/Z01-core.md).

## 1. Names (read this first)

- Nearly every zone function writes its own original name into the profiler stack on entry:
  `(&DAT_007545a8)[DAT_007549a8] = "ShineObjectClass::ShinePlayer::sp_NC_MAP_LOGIN_REQ";`
  `tools/protocol-re/names/zone/Z01.json` maps ~2750 functions to these names (`ShineObjectClass::` dropped,
  `::` → `_`, non-identifier characters → `_`; when two functions carry the same string the address is appended,
  e.g. `WorldManagerSession_wms_NC_MISC_HEARTBEAT_REQ_005a3360`). `clean.py` applies them automatically.
  To regenerate: scan `decomp.c` per function for the first `(&DAT_007545a8)[DAT_007549a8] =\s*"…";`.
  **Caveat:** a few strings are copy-paste errors in the original (`0x9884`/`0x9885` handlers say
  `…DEPOSIT_RNG`, the GameDB heartbeat says `wms_…`). Trust the registered opcode over the string.
- Hand names (`SessionPool_Pick`, `g_Objects`, the `zs_start_*` stage entry points, …) are in the same file.
- Functions Ghidra did not create (Lua C functions, a few `LAB_` handlers) can be decompiled against the
  persistent project with a small script: create the function at the address, then decompile
  (`analyzeHeadless re-data/ghidra zone -process -noanalysis -readOnly -postScript …`). Z01 did this for the
  start stages; the script is not kept in the repo (it lives in the session scratchpad), but it is 40 lines of
  `createFunction` + `DecompInterface`.

## 2. Object class hierarchy (RTTI)

```
ShineObject                                  type 0xff, vftable 933 slots
├── ShineAxialFlag      type 0               933
├── ShineDropItem       type 1               933
├── ShineMiniHouse      type 3               933
├── ShineMagicField     type 6               933
├── ShineEffectObject   type 9               933
└── ShineMobileObject   type 0xff            986
    ├── ShinePlayer     type 2               986
    ├── ShineDoor       type 7               986
    ├── ShineMover      type 11              986   (mounts / vehicles with passengers)
    └── ShineMob        type 5               992
        ├── ShineNPC      type 4             992
        ├── ShineBandit   type 8             992
        ├── ShineServant  type 10            992
        └── ShinePet      type 12            992
```

Type = `vt[0x4d0]()`. Single inheritance throughout (all base offsets 0). Other notable RTTI families:
`AxialList*` (visitors run over the objects around a point: broadcasts, scans, teleports),
`PineEventScriptNode::*` (map scripts), `ScriptInterrupt::*`, `NPCRole_*`, `MobTacticElement::*`,
`AbnormalStateContainer::*`, `UseEffect::*`, `ItemAttrCls_*`, `ZoneRingPacket*` (zone ring requests),
`InventoryLocking::InvenCellReleaser_*`, `CharClass*` (one per job). Sessions:
`ZoneBaseSession` ← `ClientSession` (← `ClientSessionNull`), `WorldManagerSession`, `GameDBSession`,
`GameLogSession`, `OPToolSession`, `ZoneListenSession`, `ZoneConnectSession`.

Print vftables: `python3 -I tools/protocol-re/rtti.py Files/Server/2016/w00_Zone00/5ZoneServer2.exe ShinePlayer`.

## 6. Conventions for reading zone handlers

- ShinePlayer handlers get `(this = player, packet)`; `packet` points at the **opcode**, so `packet+2` is payload
  offset 0. Server-link handlers (WM, GameDB, ring) get `(packet)` the same way.
- WM→zone and DB→zone messages about a player start with the 6-byte `ref` the zone put in its request:
  `{ u16 objHandle, u32 charNo }` (or `{ u16, u32 -1 }`). Handlers look the player up with
  `som_GetObject(ref.objHandle)` and usually compare `charNo` and `IsClosing`.
- Every handler checks the player mode with a static bit mask (`mask & (1 << mode)`), see Z01-core §4.3.
- Result packets to the player: `so_SendErrorCode(dept, cmd, code)` (`vt[0x308]`) = `{ u16 code }`.
- Broadcast: build an `AxialListPacketBroadcast` over `g_buf` and pass it to `so_AllInMap*`; receivers are filtered
  by mode ≠ 0, layer, sight, closing and hide-except-me (Z01-core §3.2).
- Character save: `WholeSaver` at DAT_00aa46b0: `ws_save2DB` (Character DB, dept 16) and `ws_save2worldmanager`
  (WM cache, dept 16 blobs listed in W01 §6.3).

## 7. Startup

The start sequence is a Lua script downloaded from a certification server (127.0.0.1:58492, fallback
cert1.fo.gamigo:80), decrypted with registry keys `HKLM\SOFTWARE\GBO` Natural/Desert. It calls registered
C functions `zs_service_*` / `zs_start_*`. The order is unknown (Z01-core §2). Every data table and its loader is
listed in Z01-core §2.3.
