# D01 knowledge: Account and AccountLog servers

Facts other items need. Details and evidence: `docs/pseudocode/db/D01-account.md`.

## Login result flags (answers the open question of login-server.md §7)

- 0x0C5C `nUserNo == -1` (→ Login 0x45): no `tUser` row for ID **or** e-mail + `sUserPW` + `bIsDelete = 0`, or the
  Account server's DB call failed (it then also sets `nError = 0x43`, which Login ignores). *(db-backup: usp_User_USloginGame)*
- `nUserNo == -2` (→ 0x4B) is never produced: no procedure in any backup and no code path in the Account binary writes -2.
- `nBlock != 0` (→ 0x47) = `tUser.bIsBlock` after `usp_User_chkBlock` lifted expired timed blocks *(db-backup)*.
- `bLoginAble != 1` (→ 0x48) = `tUserAuth.bIsLoginAble` of the account's `nAuthID` group (1 member, 2 closed beta, 3 test,
  9 admin) *(db-backup)*.
- 0x0C5E `bUserIPBlock` (→ 0x51) = client IP inside a `tIPBlock` range **and** the account has no `tAccountLog` row with
  `nType = 1` (never selected a world; 0x0721 writes those). `p_IPBlock_IsBlock`, AccountLog.bak copy *(db-backup)*.
  The `Fixes/` copy (2018) blocks every listed IP unconditionally.
- The 16-byte "unidentified" field Login copies into 0x0720 (reply +0x10C) is `sPassword`: failed logins store the typed
  password in `tAccountLog.sUserPassword`.

## Packet facts

- 0x0C10 NC_USER_LOGIN_DB, 0x0C11 NC_USER_LOGOUT_DB, 0x140D, 0x140E, 0x0823 are **no-ops** in the Account server, and
  0x0835 NC_MISC_HACK_SCAN_STORE_DB_CMD is a no-op in AccountLog (CheckAlive only).
- 0x082F / 0x0830 between WM and Account are NC_MISC_CONNECTFROMWHERE_DB_REQ / _ACK (PC-bang check, `usp_Pcbang_chkIP`),
  not SERVERPARAMETER: `{u16 hZone, u16 clienthandle, u32 charNo, u8 ip[4]}` → `{u16 hZone, u16 clienthandle, u32 charNo,
  u8 connectfrom}`.
- 0x0839 (Account → WM, MUNSANG event) always carries nError 0x1545; no DB access.
- 0xC801 in 2016 is 40 bytes `{u32 UserNo, char UserIP[16], Name5 spawnapps}` (the 2017 PDB inserts `UserID[30]`). AccountLog
  prints spawnapps as `client-version`.
- Raw replies with truncated u8 length bytes (wrong framing): Account 0x0C08 / 0x0C3A / 0x0C54 (len byte 0x21 for 0x121),
  AccountLog 0x0C2B (0x15 for 0x115) and 0x0C3C (0x24 for 0x124). Correctly framed: 0x0C3F, 0x0C41, 0x082D, 0x0830, 0x0839,
  0x8008, 0x800A, 0x800C and all CSendPacket replies (0x0C5C, 0x0C4C, 0x0C4E, 0x0C5E, 0x0C61, 0x0C63, 0x081E, 0x0C27, 0x2802…).
- Report error codes (0x8008/0x800A/0x800C, forwarded by WM as 0x8002/0x8004/0x8006): 0xf40 ok, 0xf41 same harmer within a
  day, 0xf42 within an hour, 0xf50 unknown report, 0xf51 older than 1 h, 0xf52 already processed, 0xf58 DB error, 0xf60 none.

## Framework

- Both servers are the same "DataServer": packets go to N worker threads, each with its own ODBC connection
  (`*this + 0x124c`; AccountLog also `*this + 0x126c` = Statistics DB). CheckAlive passes when session `+0xdc != 0`.
- CPFs server-link handlers (0x0801–0x0805, 0x0823, 0x2801–0x2807) are byte-identical in both binaries: 0x0802 requires
  `server_id_to == my type` (Account 0, AccountLog 1) and `key == to + from`, replies 0x0803 `{echo, u16 0}`.
- ODBC: SQLBindParameter = ODBC32 ordinal 72, SQLExecDirect 11, SQLCloseCursor 26, SQLFetch 13, SQLGetData 43, SQLError 10.
