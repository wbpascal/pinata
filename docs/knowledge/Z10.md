# Z10 knowledge: certification, start script, process entry

Facts from `docs/pseudocode/zone/Z10-certification.md` that other items need. § numbers refer to that file.

## For everyone working on the zone start

- **Entry chain** (§1.1): `WinMain` FUN_0049d910 → `ZoneServer::zs_start` FUN_005ab520 (ServerInfo, `ParseCmd`
  FUN_005aab10 `UPLOAD`/`REMOVE`) → `WinService::startDispatcher` → `serviceLoop` → `OnStart_Service` →
  `zs_ServiceRoutineStart` FUN_005aa770 → thread `zs_ServiceThreadFunction` FUN_005a9d90. Z01-core's "zs_start"
  FUN_005a9d90 is `zs_ServiceThreadFunction`. The service reports RUNNING before anything is loaded.
- **Start order** (from the recovered script, §4.2): data stages `sky earth black yellow home house wide tough sun moon
  full sink star sleep open long`, then run/walk factors 127 / 33, then services `iocp multisocket mainthread acceptor
  stackchecker certification`. §7.2 lists the data dependencies that force this order (D1–D12).
- **Only one fetch attempt per host** (127.0.0.1:58492, then `cert1.fo.gamigo:80`); no answer → the zone crashes
  (Z10-B6). Keys: `Files/Server/NA2016/GBO.reg` (`Natural` = N = 11113 × 11411, `Desert` = d). Cipher + Python: §3.
- The start script's Lua state is separate from the AI / scenario Lua (`LuaScriptScenario`, Z09 §14).

## For Z03 / Z09 (combat factor)

- `g_LUA_SCRIPT_SECURITYFactor.lsf_Factor` (DAT_00870dd8, Z03's `g_HitRateScale`) grows × 1.01 per world minute and
  is reset to 1.0 by the script's `dhsmfskfWk` call in the same minute block before any combat, so in a running 2016
  zone with the real script it is **1.0**; `&mobdamage` (Z11) can freeze or set it (§6.3).

## For Z02 / Z07 / Z12 (`ShineCommonParameter`, ChrCommon.txt)

- `shineparam.scp_param` = DAT_0da50470 (`ShineParameter`, 0x768 bytes, loaded by `scp_Load` FUN_004c9be0 in stage
  `house`): `chrrunspeed` +0 (127), `chrwalkspeed` +4 (33), `chrattackspeed` +8 (13), `shoutlevel` +0xC (5),
  `shoutdelay` +0x10 (2), `levellimit` +0x14 (u8, 125), `maxexpbonus` +0x18 (double, MaxExpBonus / 1000 = 3.0),
  `RestExpRate` +0x20 (1100), `MinNeedTime` +0x24 (21600), `DefaultBonusTime` +0x28 (600), `IntervalTime` +0x2C (3600),
  `AddBuffTime` +0x30 (600), `MaxBuffTime` +0x34 (7200), `LostExpLevel` +0x38 (u8, 21, DAT_0da504a8),
  `MaxFreeStat` +0x39 (u8, 180, DAT_0da504a9), `nextexp` u64[151] +0x40 (DAT_0da504b0, from StatTable `NextExp`),
  `commonparam` ptr[151] +0x4F8 (DAT_0da50968, StatTable rows: u8 level, char NextExp[50], u16 stat[28] +0x33,
  u32 ExpLostAtPvP, u8 checksum), `freestatStr/Int/Dex/Con/Men` +0x754…+0x764 (row pointer arrays,
  MaxFreeStat + 1 entries each). §5.4.
- So "g_LevelExp at DAT_0da504a8 + 8 × lv" (Z03, Z07) is `nextexp[lv − 1]`; its "level-0 entry" holds
  `LostExpLevel`, `MaxFreeStat` and padding.
- `zs_start_long` writes run/walk 5 / 10; the script restores 127 / 33. A zone started without the script moves
  players at 5/127 of normal speed (§5.4); the client (`On_NC_ACT_MOVESPEED_CMD` FUN_00499e90) applies 0x203E
  unchecked, so it shows. The 0x0830 values (shout level / delay) come from ChrCommon.txt; the 2016 client drops 0x0830
  (Z01-B5).

## Server config files (`*ServerInfo.txt`)

- `CServerInfo` over the `CCsl` script reader: row kind = CSL `dwID` (index of its `#DEFINE`: 0 MY_SERVER, 1
  NATION_NAME, 2 WORLD_NAME, 3 SERVER_INFO, 4 ODBC_INFO in the zone's file). SERVER_INFO fields: pName, nServerID,
  nWorldNo, nZoneNo, nServerIDFrom, pIP, nPort, nBackLog, nMaxAccept. Server IDs in `ServerInfo.txt`: 0 AccDB,
  1 ALDB, 2 CDB, 3 GLDB, 4 Login, 5 WM, 6 Zone; `nServerIDFrom` 20 = clients, 8 = OPTool. Lookups: Z10 §1.1 / §6.5;
  the parser and file format: Z19 (added by Z10).
