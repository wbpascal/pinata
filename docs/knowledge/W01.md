## Facts other items need

- **The WM caches the whole character** (one malloc'd blob per DB packet, session +0x560…+0x6e8) and re-sends it to
  every zone the character enters with 0x101C → 0x101F…0x1130 + 0x101D. Zones save into that cache with dept 16
  (CHARSAVE) and a few dept-4 messages. Slot ↔ opcode table: W01-core §6.3. Z01 / Z05 / D02 should treat the WM as the
  owner of character state between zones; the Character DB only sees 0x1037 at logout and the zones' own DB writes.
- **CHARDATA base blob (CharDB 0x1007, session +0x560)** offsets the WM uses: +0x00 charNo, +0x04 name[20], +0x19 u8 level,
  +0x1a u64 exp, +0x22..+0x2e stats, +0x36 u32, +0x3a u64 money ("Cen"), +0x42 map[12], +0x4e x, +0x52 y, +0x56 u8 dir (inferred),
  +0x57 u32, +0x5b u16, +0x62 u16 prison (≠0 → login map forced to "EldPri" 0x2C0/0x3C2), +0x64 u8 (level-like, checked 50..100 in 0x0861/0x0866).
- **AVATAR (0x82)**: W01-core §6.1. +0x1a slot, +0x1b loginMap[12], +0x2c race/class/gender bits, +0x7d u32 tutorialState
  (0 = not done; 3 when no tutorial row), +0x81 u8 tutorialStep. The WM forwards 0x0C13 to the client verbatim.
- **Map-login ticket**: zone must call 0x104B (NC_CHAR_REGISTNUMBER_REQ) before using the character; the WM accepts it once
  per 0x1005 (first login) or 0x180D (link reserve), and closes the WM session on an unexpected one (Z01).
- **Map change**: old zone 0x180D (dest map/x/y) → WM stores dest + ticket, replies 0x180E to the same zone; new zone's 0x101C
  gets the reserved destination in the BASE blob. 0x180B = left for a link, 0x180C = map login done, 0x0C31 = character fully
  logged out on the zone (frees `playingCharNo`).
- **0x1036 NC_CHAR_LOGIN_DB goes to the Character DB**, not to the zone (the plan text said "to zone").
- Zones register their maps with 0x180F; the WM routes `0x1001` by `Zones_FindByMap(loginMap)` and gives the client the zone's
  client-listen address from ServerInfo (0x1003).
- World-login key: Login's 0x0C0D is stored in a 0x800-slot table indexed by the XOR of the 32 validate words; 0x0C0F must
  match all 32 words, one use only. The client's `userId` in 0x0C0F is **not** compared with the stored one.
- **Correction for login-server.md §5.3**: Login's 0x0C36 is `{u16 result, u16 wmHandle, char token[32]}` (result first;
  Login FUN_00408a20 and WM FUN_00424a70 agree). 0x0808 from the WM is `{u16 currentUsers, u16 maxUsers}`.
- S2S handshake field names (from the WM's log format): 0x0802 `{u8 echo, u8 server_id_to, u8 server_id_from, u8 world,
  u8 zone, u16 key = to + from}`, 0x0803 `{u8 echo, u16 result}`. Server type ids: 0 AccountDB, 1 AccountLogDB, 2 CharDB,
  3 GameLogDB, 4 Login, 5 WM, 6 zone, 8 OPTool, 20 client (listen types).
- WM `closeReason` codes (to AccountDB 0x0C11 / AccountLog 0x0722): 0x780 logout, 0x785 double login, 0x787 not alive,
  0x788 world-login refused / DB error, 0x790 OPTool kick.
- Server parameter keys read by W01 code: `UserComeback_DaysAfterComeback`, `UserNewbie_DaysAfterSignUp`,
  `UserComeback_DaysAfterSignUp`, `UserComeback_DaysAfterLogOff`, `KQVote_LoginCoolTime`, `ChrLevel_CanCreateSen`.
- Session `userKind` (+0x1ed54): 1 normal, 2 newbie, 3 comeback; expiry at +0x1ed58. Set during world login (0x0C61/0x0C63);
  consumers are in W04/zone (not traced).
