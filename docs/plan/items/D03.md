## Item-specific guidance

- **Database backups:** read `docs/plan/db-backups.md` first (which backup is which, which version to trust). Start with `python3 -I tools/protocol-re/bak.py cover <bin>`: it lists every procedure your server calls, the backups and `Fixes/` scripts that have it, and whether the parameter count matches. For every procedure you document, print its source (`bak.py Files/Server/2016/_Database/<file>.bak proc <name>`; compare the versions when several backups have it) and use it for the tables and columns touched, the result-set column order and the meaning of each return code (the Korean header comments list them). The backups come from private servers and are not the 2016 build: confirm against the binary (parameter count of the `{CALL …}` string, `SQLGetData` order and C types, result codes checked) and mark facts only a backup shows *(db-backup)*. Say which version you used, and flag procedures that exist only as private-server work. Name tables and columns only as the procedure source spells them.
- Missing in every backup: pets (`usp_Pet_*`, 5), `usp_LinkScroll_SetDestMap`, `p_Item_MiniHouse_Effect_Resource_Del`, `p_MiniHouseURL_Get`, `p_MiniHouseURL_Set`. Gamble/slot machine, card collection, safe trade, auto-mon and belonged items exist only in `w00_Character`. The gem enchant procedures (`usp_Item_*Enchant*`, author `<KHRISMIZER>`) may be private-server work. `p_Item_BuyAll` and `p_Item_BuyLot` match the binary only in `w00_Character` (the older copy has one parameter fewer). `Fixes/` changed `usp_ChargeItem_Draw` and `usp_ChargeItem_GetList` (premium inventory slots): compare with `Character.bak`.
- Open from Z07 (§7): after `0xC412 NC_COLLECT_REWARD_DB_ACK` the zone does not add the RewardID to its rewarded list, so a player can request the same card reward again in one session. Say whether the 0xC411 procedure refuses an already-given RewardID (if not, it is an original bug to add to Z07's list via X01). 0xC411 also carries a new item key and attribute (0x77 bytes in 2016; the 2017 struct is 8 bytes).
- Open from Z07 (§9): pet create/load/rename (0xD40D / 0xD40B / 0xD403) and their result codes 0x3408 / 0x3420 / 0x3418 as the zone expects them.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/D03.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/D03.json`) and verified layouts (`docs/protocol/annotations/D03.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/D03.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/D03.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.

## Rules

- Only write your own files: `docs/pseudocode/db/D03-character-items.md`, `docs/knowledge/D03.md`, `docs/plan/status/D03.md`,
  `tools/protocol-re/names/<bin>/D03.json`, `docs/protocol/annotations/D03.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
