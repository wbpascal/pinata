# Z10: Zone: certification and the downloaded start script

**Phase:** 2 · **Depends on:** Z01 · **Output:** `docs/pseudocode/zone/Z10-certification.md`

## Goal

The zone does not start on its own: it downloads an encrypted Lua script from a certification server (127.0.0.1:58492, fallback cert1.fo.gamigo:80), decrypts it with registry keys HKLM\SOFTWARE\GBO `Natural`/`Desert` and runs it; the script calls the registered `zs_service_*` / `zs_start_*` stages (Z01-core §2). Only the zone uses this (no other server binary has these strings). The original Gamigo script is lost, but a working replacement answer exists: the NA2016 service `_GamigoZR` (`Files/Server/NA2016/GamigoZR/GamigoZR.exe`) serves it on 127.0.0.1:58492 (S01 §1.5). Reconstruct the mechanism, decrypt that answer to recover the script it carries, and from both state what the script must do, so a rebuilt server knows which stage order and which values to use, and whether the certification can stop the server.

## Item-specific guidance

- Read `docs/pseudocode/zone/Z01-core.md` §2 and `docs/knowledge/Z01.md` §1/§7 first. The stage functions and several entry points are not in `decomp.c`; decompile them against the persistent Ghidra project with a headless script (`analyzeHeadless re-data/ghidra zone -process -noanalysis -readOnly`, `createFunction` + `DecompInterface`), as Z01 did.
- Request/response: `FetchStartScript` FUN_005b07a0 and its callees FUN_00613440 (request build/send), FUN_00613750 (key setup from the two registry int64s), FUN_00613950 (decrypt), FUN_005d6d40 (Lua dostring). Document the wire format, what the request carries (world/zone numbers, version?), the `[a][b]` header checks (1 ≤ a ≤ 0x2760, b < 11) and the cipher as pseudocode with test vectors if possible.
- The GamigoZR answer (S01 §1.5, read it first): a .NET 4 Windows service "Gamigo_Zone_Response_Service" (2019, private-server tool, installed by `install.bat` / `_Install Services.ps1` as `_GamigoZR` and started 5 s before the zones by `Start Services.ps1`), an `HttpListener` on `http://127.0.0.1:58492/` (the zone's primary certification address; the zone falls back to cert1.fo.gamigo:80, which no longer answers). Its UTF-16 strings hold the header `[10000][10][{( USA V.0.001 )}]` and 42 hex lines (2 680 hex digits). Read its IL (e.g. `monodis`/`ilspycmd` if installed, else parse the .NET metadata with Python) to get the line order and the exact HTTP reply (status, headers, body framing), check that the header passes the `[a][b]` checks, then decrypt the body with the zone's cipher. The registry keys `Natural`/`Desert` are not in the repo: look for them in the NA2016 files (`*.reg`, `*.ps1`, `*.bat`, readme) and, if absent, say whether the cipher can be solved without them (known plaintext: the script must call `zs_*` names). If the decrypted script is recovered, document it in full: it replaces the inferred stage order below and gives the real values (run/walk factors, server parameters). Do not run the service or the zone.
- Threads: `zs_service_certification` (thread FUN_005ab9c0) and `zs_service_stackchecker` (thread FUN_005a9f10). What do they check, how often, against what, and what happens on failure (log, shutdown, silent misbehaviour)? Look for time/expiry checks (`dhsmfskfWk` date helper, DAT_00aa43b8).
- The Lua surface: list every C function the script can call (FUN_005d7ca0 and any other `lua_setglobal` registrations), with arguments and effects. In particular the run/walk factors (`ekfflrlthreh` / `rjerlthreh` → 0x203E move speed) and any writer of the 0x0830 server parameters (DAT_0da5047c / DAT_0da50480). Check whether the script can read or set other globals.
- Infer the stage order from data dependencies between the stages (e.g. Field.txt before NPCs, packet tables before listeners, `zs_start_open` last) and from the Message.txt labels. Give one recommended order with the reason for each constraint, marked *(inferred)*.
- Diff with the 2015 zone (`Files/Server/2015/w00_Zone00`) only to see whether the mechanism changed; do not document 2015 otherwise.
- If a capture of a live zone start ever appears in `re-data/captures/`, it overrides inference.
- End with a recommendation for a rebuild: which values to hard-code, what to leave out.

## Done when

Request/response and cipher documented; both threads explained with their failure behaviour; Lua surface listed; a recommended stage order with reasons; rebuild recommendation written.

## How to work

**One part per session.** Context is re-read on every turn, so a long session costs far more than several short ones.
This item has no scope table: in the first session, split the work into parts of similar size (about 2500 decompiled lines each, plus a sweep part and a review part) and write the list into the status file. At the start, read `docs/plan/status/Z10.md` (its **State** line and **Working notes**) and take the first part
not done (no status file: part 1). Do only that part, close it (step 6) and end the session, even if context is left.

1. `AGENTS.md` is already in your context (do not re-read it); follow its **Context budget** section. Part 1 only: read
   `docs/plan/00-master-plan.md`. Later parts: the status file's working notes replace it; do not re-derive what they record.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for this part: the `docs/knowledge/*.md` sections of the items you depend on that touch it, and the
   `opcodes-*.md` / `packets-*.md` rows of its opcodes (one `rg -i -M 300 -e 0x<op> -e 0x<op> …
   docs/protocol/packets-<bin>.md` for all of them). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need. This
   includes your own output file: from part 2 on, never read it whole; use its outline and the sections you extend.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_(<NAME>|<NAME>)$'` (one regex for
   several; field names, offsets, sizes; also server-internal packets and shared enums/structs). It is a newer build:
   confirm against the 2016 code and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For the handlers of this part, in scope-table order, a few related handlers (one opcode family) at a time:
   - read them together: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin>
     <addr> <addr> …` (the only way to read code; never `sed`/`cat` on `decomp.c`). Registrations and sends of all of
     them in one query: `jq -c '.tables[].entries[] | select(.handler|IN("<FUN_…>","<FUN_…>"))' re-data/exports/<bin>/handlers.json`

   - write their pseudocode blocks (`@ FUN_…`), with field names, checks, state changes, replies, error codes

   - record new names (`names/<bin>/Z10.json`) and verified layouts (`docs/protocol/annotations/Z10.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants. Write each
   in the part that first reaches it and note it in the working notes so later parts link to it instead of re-reading.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. The sweep part then checks for what was missed: `rg` your
   subsystem's strings, SHN tables and opcodes (`opcodes.json`) for functions never opened, check every caller and callee
   of the documented functions, and every unnamed `FUN_` left in the text, and run
   `python3 -I tools/protocol-re/coverage.py Z10` (functions reachable from your handlers that no doc cites yet,

   `**State:** done` after the review part). Then: done handlers per part, remaining work, and **Working notes**: only what

   Commit on the current branch (`Z10 part <n>: <what>`), then end the session. If context runs low before the part is
   done, finish the handler in hand, record the rest of the part as remaining, commit and end the same way.
