# Z10: Zone: certification and the downloaded start script

**Phase:** 2 · **Depends on:** Z01 · **Output:** `docs/pseudocode/zone/Z10-certification.md`

## Goal

The zone does not start on its own: it downloads an encrypted Lua script from a certification server (127.0.0.1:58492, fallback cert1.fo.gamigo:80), decrypts it with registry keys HKLM\SOFTWARE\GBO `Natural`/`Desert` and runs it; the script calls the registered `zs_service_*` / `zs_start_*` stages (Z01-core §2). Only the zone uses this (no other server binary has these strings). The script itself is not recoverable. Reconstruct the mechanism around it and infer what the script must do, so a rebuilt server knows which stage order and which values to use, and whether the certification can stop the server.

## Item-specific guidance

- Read `docs/pseudocode/zone/Z01-core.md` §2 and `docs/knowledge/Z01.md` §1/§7 first. The stage functions and several entry points are not in `decomp.c`; decompile them against the persistent Ghidra project with a headless script (`analyzeHeadless re-data/ghidra zone -process -noanalysis -readOnly`, `createFunction` + `DecompInterface`), as Z01 did.
- Request/response: `FetchStartScript` FUN_005b07a0 and its callees FUN_00613440 (request build/send), FUN_00613750 (key setup from the two registry int64s), FUN_00613950 (decrypt), FUN_005d6d40 (Lua dostring). Document the wire format, what the request carries (world/zone numbers, version?), the `[a][b]` header checks (1 ≤ a ≤ 0x2760, b < 11) and the cipher as pseudocode with test vectors if possible.
- Threads: `zs_service_certification` (thread FUN_005ab9c0) and `zs_service_stackchecker` (thread FUN_005a9f10). What do they check, how often, against what, and what happens on failure (log, shutdown, silent misbehaviour)? Look for time/expiry checks (`dhsmfskfWk` date helper, DAT_00aa43b8).
- The Lua surface: list every C function the script can call (FUN_005d7ca0 and any other `lua_setglobal` registrations), with arguments and effects. In particular the run/walk factors (`ekfflrlthreh` / `rjerlthreh` → 0x203E move speed) and any writer of the 0x0830 server parameters (DAT_0da5047c / DAT_0da50480). Check whether the script can read or set other globals.
- Infer the stage order from data dependencies between the stages (e.g. Field.txt before NPCs, packet tables before listeners, `zs_start_open` last) and from the Message.txt labels. Give one recommended order with the reason for each constraint, marked *(inferred)*.
- Diff with the 2015 zone (`Files/Server/2015/w00_Zone00`) only to see whether the mechanism changed; do not document 2015 otherwise.
- If a capture of a live zone start ever appears in `re-data/captures/`, it overrides inference.
- End with a recommendation for a rebuild: which values to hard-code, what to leave out.

## Done when

Request/response and cipher documented; both threads explained with their failure behaviour; Lua surface listed; a recommended stage order with reasons; rebuild recommendation written.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/Z10.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/Z10.json`) and verified layouts (`docs/protocol/annotations/Z10.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/Z10.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/Z10.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
