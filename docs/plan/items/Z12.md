# Z12: Zone: stat calculation, level/exp, login data parsing (added by Z07)

**Phase:** 2 · **Depends on:** Z03, Z07 · **Output:** `docs/pseudocode/zone/Z12-stats.md`

## Goal

Z07 documented the packets around stats and login but not the code that computes stats or reads the login data. Reconstruct the full stat model (every stat-matrix layer, max HP/SP/LP, stones), the level/exp tables and level-up side effects, and how the zone parses each WM login blob into the player object.

## Item-specific guidance

- Read `docs/pseudocode/zone/Z07-character.md` §1–§2 and `docs/knowledge/Z07.md` first; Z03 §2 has the matrix formula `Total = (L0+L1)·L12·L10·L4·L14/10¹² + L5+L7+L9+L11+L13` and Z07 §1.5 confirmed layer 0 = base, 15 = total.
- `so_allparametercalculate` (vt 0x57c, FUN_0054f190): what fills each layer (class base stats per level from class data `p.vt[0x49c]() + 0x10858`, stat points via FUN_00517b60, items, upgrades, passives, abstates, titles, charged buffs `p+0x2a5a0`), and the order. MaxHP FUN_0054a670, MaxSP FUN_0055a8b0, MaxLP vt 0xd94, HP/SP stone maxima (`p+0x2a5a2/a4`). Which packets the refresh `vt 0x528` and `smo_NotifyParameterChange` (vt 0x34) send.
- Level/exp: `g_LevelExp` (DAT_0da504a8, u64 per level; Z07 found that the per-stat cap DAT_0da504a9 lies inside its level-0 entry: explain), the stat-point table DAT_0da50968 (loader, file, columns), exp gain and level-up side effects (FUN_0058bd10, reward table DAT_14d42940), level-up packets. Check Z03's output first so exp on kill is not documented twice.
- Login blob parsing (dispatch table in Z07 §1.2): `so_charsharpdata` FUN_0044ae80, `so_StoreQuestDoing/Done/Read` FUN_0044b3c0 / FUN_0044b500 / FUN_0044b640 / FUN_0044b770, `so_CharAbstateData` FUN_0044e0e0, `so_charskilldata` FUN_0044bf20, `so_CharChargedBuffData` FUN_0044e1e0, `so_charpassivedata` FUN_0044e5a0, `so_StoreInventoryFromServer` FUN_0044ddf0, `so_Storegamedata` FUN_0044c220, `so_ply_Getchestinform` FUN_0044c8a0, and the builder `vt 0x4b4` FUN_0055ab60. Give each body layout (compare the PDB `PROTO_NC_CHAR_*_CMD` structs and W01 §6.3) and the player members it fills.
- Smaller open points from Z07 §12: 0x10D3 NC_CHAR_ZONE_SINGLE_OPTION_CMD fields (FUN_0059d510, FUN_00560340, FUN_00560a10, vt 0xae8), the 0x10B8 LINK_FROM record (FUN_00444970, FUN_00570b30), the title progress reset rule FUN_0062e120 (0x1031).

## Done when

Every stat-matrix layer has a named source; level/exp tables and level-up documented; every login blob has a body layout and the members it fills.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/Z12.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/Z12.json`) and verified layouts (`docs/protocol/annotations/Z12.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/Z12.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/Z12.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
