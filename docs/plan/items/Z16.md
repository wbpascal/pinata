# Z16: Zone: kingdom quest element and guild tournament system (added by Z08)

**Phase:** 2 · **Depends on:** Z08 · **Output:** `docs/pseudocode/zone/Z16-events.md`

## Goal

Z08 §4 and §8 documented the kingdom-quest (KQ) and guild-tournament packets. The per-event state behind them (KQ element, players, scores, rewards; the tournament system attached to a map) is not reconstructed.

## Item-specific guidance

- Read `docs/pseudocode/zone/Z08-content.md` §4, §8 and §15 and `docs/knowledge/Z08.md` first. Map scripts themselves (ScenarioBookShelf, `PineEventScriptNode::*`) belong to Z09; document here only the KQ/GT objects they call.
- KQ: `KingdomQuest::KQElement` (`kqe_QuestStart`, `kqe_ReviveNumber`, `kqe_SetLimitTime`), `KQPlayerInfoList` (add/remove, knock-down counters, `kqpil_PlayerInformFunc`), `KingdomQuestContainer` (`g_KingdomQuests`, `kqc_MapUseCheck`), `KQContribute::KQContributeList` (`g_KQContribute`: `kqcl_NewKQ`, `kqpl_EndOfKQ`, how scores are counted), the end of a KQ and the reward request `0x5815 NC_KQ_REWARD_REQ` (who sends it: `cQuestResult`, `cQuestResult_Individual`, `PineEventScriptNode::ShineQuestResult`, `cEndOfKingdomQuest`), the KQ client packets sent during the event (grep `= 0x58` sends in the zone export), and the GM commands `&kingdomquest` / `&EndOfKingdomQuest` / `&Reroadkingdomquest`.
- Guild tournament: `FieldMap_fm_GetGuildTournamentSystem` and the GT system class (flag capture end callback FUN_00477c00, `FUN_00479510` flag check, guild skills `FUN_0047b9a0`, dice game `FUN_0047af20`, observers FUN_004788c0, member grades FUN_0047ccd0), the seed table DAT_0d55a3e0 / DAT_0d55a860, `wms_GuildTournamantStart`, `so_ply_Summon2GuildTournament` FUN_00478750, the join check FUN_00476860 (0x74E3 → 0x74E5), the match end and result reporting to the WM (W03 has the WM side), and the client packets 0x74xx sent during a match.
- Settle Z08-B12 (seed bound 33 vs 32) and the 0x1A41/0x1A42 mode-vs-location order of 0x74AC (read the assembly).

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/Z16.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/Z16.json`) and verified layouts (`docs/protocol/annotations/Z16.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/Z16.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/Z16.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
