# S01: 2016 server PDBs (NA2016): official names, types and packet layouts for the exact build

**Phase:** 1 · **Depends on:** C02 · **Output:** `docs/knowledge/S01.md + docs/protocol/pdb2016-layouts.json + names/<bin>/S01.json`

## Goal

`Files/Server/NA2016/` holds the **same builds** as `Files/Server/2016/` (identical PE timestamps and RSDS GUID/age) plus the full private PDBs of Login, WorldManager, Zone, Account and AccountLog (no PDB for Character and GameLog). The PDBs therefore describe the 2016 code exactly: function and global names, class layouts (`ShineObjectClass::ShinePlayer` 0x2c058 bytes, absent from the 2017 client PDB), enums, and 2016 `PROTO_NC_*` packet structs (Zone 1286, WM 1218; e.g. `PROTO_NC_MAP_LOGIN_REQ` has `Name8[49] checksum`, 2017 has 50). Make that the top name/type/layout source and give every finished item a follow-up list.

## Item-specific guidance

- Already done when the plan was written (2026-11-13): `re-data/exports/<bin>-pdb/` (login, wm, zone, account, accountlog) = the **unpatched 2016 exes** analysed with the NA2016 PDB loaded (`reanalyze.sh <bin>-pdb <exe> <pdb>`); every old function address is kept, separators carry qualified names (`CParserClient::fc_NC_…`). `tools/protocol-re/pdb_names.py` wrote `names/<bin>/S01.json` (official names for addresses no item had named; item files still win) and `docs/knowledge/S01-renames.tsv` (our name → official name per item). The old exports stay the input of `extract.py`/`layouts.py` (they pattern-match `FUN_`/`DAT_` names).
- Do not analyse the NA2016 exes: their `.reloc` section was replaced by a `custom` section holding private-server hook patches (WM: jmp hooks at 004135b4, 00414b51, 00417765, 00417a58, 0041c7ae, …; Zone: 00458d66 and 00459158 clamp a count to 0x20, plus byte edits at 00470265 and 00598580). Decode each patch (target code in the `custom` section, VA = image base + section RVA) and record what it changes: each is a hint at an original bug. List them in `docs/knowledge/S01.md` with the owning item, for X01's bug register.
- Packet layouts: write `docs/protocol/pdb2016-layouts.json` with `pdb.py <server pdb> layouts` for all five PDBs (merge; a dept present in several PDBs should agree, list disagreements) and make `regen.sh`, `packets.py`, `pcap_decode.py` and `make_dissector.py` prefer it over `pdb-layouts.json` (label `pdb2016`, ranked below hand annotations, above `pdb2017`). Opcode names: add the server enums to `catalog.py` the same way (`pdb2016` above `handler`/`client`). Report opcode/struct differences 2016 vs 2017 in the knowledge file.
- Per-item follow-up table in `docs/knowledge/S01.md` (same format as the C02 table in the master plan): per finished item, how many of its names get official names (`S01-renames.tsv`), which of its hand layouts / member offsets differ from the PDB (Z01's ShinePlayer offsets vs `pdb.py … types '^ShineObjectClass::ShinePlayer$'`), which of its `(ours)` names and `(pdb2017)` facts the 2016 PDB settles. Do not edit other items' files.
- Types catalogue: which server types matter to which item (ShinePlayer/ShineMobileObject/ShineNPC members, item/abstate/skill classes, WM session and guild classes, SHN row structs vs `shn.py` column names). Point to `pdb.py <pdb> types REGEX` instead of copying dumps.
- Third-party docs (local only, gitignored): `re-data/external/fiestaheroes/` = clone of github.com/FiestaHeroes/Documentation (doc.fiestaheroes.com, documents the NA2016 set): Lua API (`docs/Lua Scripting/documentation.md`, `static/files/fiesta.lua`, 243 of 245 names occur in the zone strings), 86 SHN table pages, DB tables, GM commands. Map each to the items that should cross-check it (Z09 Lua/AI, Z11 GM commands, Z07/Z12/Z17 SHN columns, D0x tables). Evidence label *(fh-doc)*: third-party interpretation, below code.
- Data: `Files/Server/NA2016/9Data` differs from `Files/Server/2016/9Data` in ~37 files of content (the other ~1100 differ only by CRLF). List them; say which set the binaries' loaders accept if the code shows it (column counts, file names). The NA2016 DB backups add one Character procedure and `Options.bak` (tables only): note, nothing more.

## Done when

`pdb2016-layouts.json` and server opcode names used by the generated docs; NA2016 patches decoded; per-item follow-up table and types catalogue in `docs/knowledge/S01.md`; `regen.sh` run.

## How to work

**One part per session.** Context is re-read on every turn, so a long session costs far more than several short ones.
This item has no scope table: in the first session, split the work into parts of similar size (about 2500 decompiled lines each, plus a sweep part and a review part) and write the list into the status file. At the start, read `docs/plan/status/S01.md` (its **State** line and **Working notes**) and take the first part
not done (no status file: part 1). Do only that part, close it (step 6) and end the session, even if context is left.

1. `AGENTS.md` is already in your context (do not re-read it); follow its **Context budget** section. Part 1 only: read
   `docs/plan/00-master-plan.md`. Later parts: the status file's working notes replace it; do not re-derive what they record.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for this part: the `docs/knowledge/*.md` sections of the items you depend on that touch it, and the
   `opcodes-*.md` / `packets-*.md` rows of its opcodes (one `rg -i -M 300 -e 0x<op> -e 0x<op> …
   docs/protocol/packets-<bin>.md` for all of them). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need. This
   includes your own output file: from part 2 on, never read it whole; use its outline and the sections you extend.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_(<NAME>|<NAME>)$'` (one regex for
   several; field names, offsets, sizes; also server-internal packets and shared enums/structs). It is a newer build:
   confirm against the 2016 code and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For the handlers of this part, in scope-table order, a few related handlers (one opcode family) at a time:
   - read them together: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin>
     <addr> <addr> …` (the only way to read code; never `sed`/`cat` on `decomp.c`). Registrations and sends of all of
     them in one query: `jq -c '.tables[].entries[] | select(.handler|IN("<FUN_…>","<FUN_…>"))' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate), again several per `clean.py` call
   - write their pseudocode blocks (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/S01.json`) and verified layouts (`docs/protocol/annotations/S01.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants. Write each
   in the part that first reaches it and note it in the working notes so later parts link to it instead of re-reading.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. The sweep part then checks for what was missed: `rg` your
   subsystem's strings, SHN tables and opcodes (`opcodes.json`) for functions never opened, check every caller and callee
   of the documented functions, and every unnamed `FUN_` left in the text, and run
   `python3 -I tools/protocol-re/coverage.py S01` (functions reachable from your handlers that no doc cites yet,
   largest first; cite each one you cover as `FUN_…` so it counts). Stopping early because the handlers are
   "done" is the most common gap in past items; reviews keep finding uncovered cases that were in scope.
6. Close the part: update `docs/plan/status/S01.md`. Its first line is `**State:** part <n> of <total> done` (or
   `**State:** done` after the review part). Then: done handlers per part, remaining work, and **Working notes**: only what
   later parts need and cannot cheaply re-read (struct and member offsets, helper names and meanings, shared state, open
   questions for a later part, next free bug ID `S01-B<n>`). Keep the notes short; every later session reads them.
   Commit on the current branch (`S01 part <n>: <what>`), then end the session. If context runs low before the part is
   done, finish the handler in hand, record the rest of the part as remaining, commit and end the same way.
   **Re-split when the parts are wrong.** The Parts table is sized from handler lines only; work outside the handlers
   (internals, tables, timers, the "also" list) is not counted. If a part still open looks too big for one session (or
   two are small enough to merge), write the new split as a **Parts** list in the status file (e.g. add part `3b`, with
   what it covers) and use its count as `<total>`; from then on the status file's list replaces the table. Do not edit
   this plan file (it is generated).
7. Sweep part, at the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/S01.md` (facts others need), add the
   original-server bugs table and an "uncertain / not reconstructed" section to your output.
8. Also end your output with a "Coverage boundary" section: one row per thing you found but did not cover (function,
   packet, table, behaviour) with an argument why it is out of bounds for this item: either the existing item that
   covers it (ID and the line of its plan or scope table that includes it) or, if no item does, a proposed new item
   (title, scope, why it does not fit here) added to `docs/plan/status/S01.md` under "Proposed follow-up items" for the
   user to accept. "Too large" or "ran out of context" is not out of bounds: that is unfinished work for the status file.
9. Review part: **review with fresh context** before marking the item done. The reviewer must not share your reading
   of the code. The review task is `docs/plan/review-prompt.md` (with `<ID>` = `S01`).
   - If your agent tool can start a fresh-context subagent (not a fork of your session), give it that file's text with
     `<ID>` replaced by `S01`, and wait for its numbered findings list.
   - Otherwise stop here: set the status file to "awaiting review" and end the session. The user runs the review as a
     separate session ("Review work item S01 as described in `docs/plan/review-prompt.md`") and then resumes this item,
     whose session finds the findings under "Review findings" in `docs/plan/status/S01.md`.
   Fix every finding in your files, or write in `docs/plan/status/S01.md` under "Review" why you reject it. Re-run
   `coverage.py S01` and `regen.sh`, record the before/after coverage line in the status file, then mark the item done.
