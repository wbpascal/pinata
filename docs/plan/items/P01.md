# P01: Packet capture decoder

**Phase:** 1 · **Depends on:** nothing (can start immediately) · **Output:** `tools/protocol-re/pcap_decode.py + docs/knowledge/P01.md`

## Goal

A pure-Python (stdlib only: no scapy/dpkt/tshark on this machine) tool that turns a capture of real client↔server traffic into a decoded, annotated packet log, and checks it against our documentation. It must work before any capture exists: test it on synthetic captures it generates itself.

## Item-specific guidance

- Captures are recorded with Wireshark on the (Windows) PC running the game and copied here. tshark is NOT available on this machine, so parse the files directly.
- Input: `.pcapng` (primary, Wireshark default) and `.pcap`; link types Ethernet, Npcap loopback (DLT_NULL/LOOP) and raw IP; IPv4 TCP. Read pcapng **packet comments** (EPB `opt_comment`) and show them in the decoded log as markers. P02 uses them to tie packets to the user's actions. Reassemble each TCP stream by sequence number (handle retransmits and out-of-order data, report gaps).
- Classify streams by server port from `Files/Server/2016/9Data/ServerInfo/ServerInfo.txt` (type-20 client ports: Login 9010, WM 9110, zones 9210/9212/9214/9216). Make the port map overridable on the command line (a live server may use other ports).
- De-frame per `docs/protocol/README.md` §1.1. Decrypt client→server bodies with the XOR-499 table (Appendix A) starting at `seed % 499` from the stream's first server→client `0x0807`. The index runs on across packets. If the seed was not captured, brute-force the start index (499 candidates) by checking that decrypted opcodes are known.
- Decode each packet using `docs/protocol/opcodes.json` (name), `annotations.json` + `annotations/*.json` (verified fields, preferred), and `re-data/exports/<bin>/layouts.json` (generated fields, marked as such). Unknown regions → hex.
- Validation report per packet type: count, observed payload sizes vs documented size, fields whose observed values contradict documented constants or ranges, opcodes never documented, documented C→S checks violated (e.g. length checks), and bytes the docs leave undocumented that are not always zero.
- Outputs: `<capture>.decoded.txt` (time, direction, server, opcode, name, fields), `<capture>.report.md`, and `<capture>.json` (machine-readable for P02). Mask the password field of `0x0C5A` by default (`--show-secrets` to keep it).
- Self-test: `pcap_decode.py --selftest` builds a synthetic pcap (seed, encrypted 0x0C65/0x0C5A, server 0x0C0A, a long-form packet ≥256 bytes, a TCP segment split across two frames) and asserts that decoding round-trips.
- Document usage and limits in `docs/knowledge/P01.md` and add a short section to `docs/protocol/README.md`.

## Done when

`--selftest` passes; decoding a synthetic capture yields correct opcodes, decrypted payloads and a report; usage documented.

## How to work

1. `CLAUDE.md` is already in your context (do not re-read it); follow its **Context budget** section. Read
   `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for your area: `docs/plan/status/P01.md` (resume from it if present), the `docs/knowledge/*.md`
   of the items you depend on, and the `opcodes-*.md` / `packets-*.md` rows of your opcodes
   (`rg -i -M 300 '0x<op>' docs/protocol/packets-<bin>.md`). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
     (the only way to read code; never `sed`/`cat` on `decomp.c`). Its registration and sends:
     `jq -c '.tables[].entries[] | select(.handler=="<FUN_…>")' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/P01.json`) and verified layouts (`docs/protocol/annotations/P01.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/P01.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/P01.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
