# P03: Wireshark dissector (Lua plugin, generated from the docs)

**Phase:** 1 · **Depends on:** P01 (soft: its synthetic capture is a handy test file) · **Output:** `tools/protocol-re/make_dissector.py → tools/wireshark/fiesta.lua + docs/knowledge/P03.md`

## Goal

Let the user see decrypted, named, field-decoded Fiesta packets live in Wireshark on the PC that runs the game, so they can comment packets accurately while recording. The plugin is generated from our docs and rebuilt by `regen.sh`, so it improves as other items add names and layouts.

## Item-specific guidance

- Wireshark is not installed on this machine; the user installs the plugin on the capture PC (Windows): copy `fiesta.lua` to `%APPDATA%\Wireshark\plugins\` (or the global plugins folder) and restart Wireshark / Ctrl+Shift+L. Document this.
- Register on the type-20 client ports from `Files/Server/2016/9Data/ServerInfo/ServerInfo.txt` (9010, 9110, 9210/9212/9214/9216) and expose the port list as a protocol preference.
- Framing via `dissect_tcp_pdus` (handles TCP segmentation): length = 1-byte form, or 0x00 + u16 long form (`docs/protocol/README.md` §1.1). One Fiesta packet per subtree; several per TCP segment.
- Decryption of client→server bodies: XOR-499 table (README Appendix A), start index = `seed % 499` from the server's `0x0807` on the same conversation, advancing across packets. Wireshark re-dissects packets in any order, so compute the index **once** on the first pass (`not pinfo.visited`) and cache it per frame + PDU offset (and the running index per conversation). Show both raw and decrypted bytes (new data source tab).
- Opcode → name from `docs/protocol/opcodes.json` (dept/cmd shown too); fields from `annotations.json` + `annotations/*.json` (verified, preferred) and `re-data/exports/<bin>/layouts.json` (generated, labelled "guess"). Field types u8/u16/u32/i16/i32/char[n]/bytes; structs like AVATAR/WORLD as repeated subtrees with count fields.
- Expert info for: unknown opcode, payload shorter/longer than documented, packet before seed (cannot decrypt).
- Mask the `0x0C5A` password field by default (preference to show it).
- Make `make_dissector.py` part of `tools/protocol-re/regen.sh`.
- Testing without Wireshark here: keep framing/decrypt logic in pure Lua functions and test them with a standalone `lua` interpreter if one is installed (`which lua`). Otherwise port the same test vectors from P01's self-test into a Python check of the generated tables. Ask the user to confirm the plugin on their PC with P01's synthetic capture and a real one.

## Done when

`fiesta.lua` generated by `regen.sh`; decryption and framing logic tested; installation and usage documented in `docs/plan/capture-guide.md` (section "Live decoding in Wireshark") and `docs/knowledge/P03.md`.

## How to work

1. `AGENTS.md` is already in your context (do not re-read it); follow its **Context budget** section. Read
   `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for your area: `docs/plan/status/P03.md` (resume from it if present), the `docs/knowledge/*.md`
   of the items you depend on, and the `opcodes-*.md` / `packets-*.md` rows of your opcodes
   (`rg -i -M 300 '0x<op>' docs/protocol/packets-<bin>.md`). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
     (the only way to read code; never `sed`/`cat` on `decomp.c`). Its registration and sends:
     `jq -c '.tables[].entries[] | select(.handler=="<FUN_…>")' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/P03.json`) and verified layouts (`docs/protocol/annotations/P03.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. Before you finish, sweep for what you missed: `rg` your subsystem's
   strings, SHN tables and opcodes (`opcodes.json`) for functions you never opened, check every caller and callee of the
   functions you documented, and every unnamed `FUN_` left in your text, and run
   `python3 -I tools/protocol-re/coverage.py P03` (functions reachable from your handlers that no doc cites yet,
   largest first; cite each one you cover as `FUN_…` so it counts). Stopping early because the handlers are
   "done" is the most common gap in past items; reviews keep finding uncovered cases that were in scope.
6. Every ~10 handlers, update `docs/plan/status/P03.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/P03.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
8. Also end your output with a "Coverage boundary" section: one row per thing you found but did not cover (function,
   packet, table, behaviour) with an argument why it is out of bounds for this item: either the existing item that
   covers it (ID and the line of its plan or scope table that includes it) or, if no item does, a proposed new item
   (title, scope, why it does not fit here) added to `docs/plan/status/P03.md` under "Proposed follow-up items" for the
   user to accept. "Too large" or "ran out of context" is not out of bounds: that is unfinished work for the status file.
9. **Review with fresh context** before marking the item done. The reviewer must not share your reading of the code.
   The review task is `docs/plan/review-prompt.md` (with `<ID>` = `P03`).
   - If your agent tool can start a fresh-context subagent (not a fork of your session), give it that file's text with
     `<ID>` replaced by `P03`, and wait for its numbered findings list.
   - Otherwise stop here: set the status file to "awaiting review" and end the session. The user runs the review as a
     separate session ("Review work item P03 as described in `docs/plan/review-prompt.md`") and then resumes this item,
     whose session finds the findings under "Review findings" in `docs/plan/status/P03.md`.
   Fix every finding in your files, or write in `docs/plan/status/P03.md` under "Review" why you reject it. Re-run
   `coverage.py P03` and `regen.sh`, record the before/after coverage line in the status file, then mark the item done.
