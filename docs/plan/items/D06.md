# D06: Database behaviour the backups do not give us (added by D02; run last, before X01)

**Phase:** 2 · **Depends on:** D01, D02, D03, D04, D05 · **Output:** `docs/pseudocode/db/D06-db-inferred.md`

## Goal

D01–D05 describe what each DB server does around its stored procedures and take the procedure bodies from the private-server backups (`docs/plan/db-backups.md`). Some procedures the 2016 binaries call have no source anywhere or a different parameter count, and several statements about what the database does are only *(inferred)*. A rebuild has to write these procedures itself. Collect every such gap, infer as far as the evidence allows what each procedure reads, writes and returns, and the table schema behind it, and write the result as a spec a rebuild can implement.

## Item-specific guidance

- Scope, taken at the end of D02 (re-run `python3 -I tools/protocol-re/bak.py cover <bin>` for `account`, `accountlog`, `character`, `gamelog` first; it may have changed). No source anywhere: account `p_UserKey_Get_FromAccount`, `p_UserPlayRemainTime_Get_FromAccount`, `p_UserPlayRemainTime_Set_FromAccount`, `usp_Event_addCash`, `usp_JPUser_insert`, `usp_Pcbang_chkIP`, `usp_TWUser_insert`, `usp_User_LoginNetmarble`; accountlog `p_Event_L20_Get`, `p_Event_L20_Set`, `p_SameTimeCharClass_Add`, `usp_AccountLog_GetDateDiffLastlogout`; character `p_Guild_SetMoney`, `p_IsPromotionUser`, `p_Item_MiniHouse_Effect_Resource_Del`, `p_MiniHouseURL_Get`, `p_MiniHouseURL_Set`, `p_Promotion_Get`, `p_Promotion_Set`, `usp_CharacterLoadingDetailInfo`, `usp_GuildTournament_setRefundNotice`, `usp_LinkScroll_SetDestMap`, `usp_Pet_getInfo`, `usp_Pet_setCreate`, `usp_Pet_setDelete`, `usp_Pet_setName`, `usp_Pet_setTendency`; gamelog `usp_Login_setChannel`. Parameter count differs from the backups: account `usp_User_LoginGame` (5 vs 6), character `usp_Character_setFriendpoint` (2 vs 3), `usp_CharacterLoading` (11 vs 6).
- Also in scope: call strings built at run time (character `SQL_BuildCallString` FUN_00460bf0, e.g. `p_Char_SetStateWithSetItemAndRestTime`; `docs/knowledge/D02.md`), which `cover` does not see: find every caller and check each name against the backups. And every *(inferred)* or *(db-backup)* statement about database behaviour in the D01–D05 outputs (their "Not reconstructed / uncertain" sections, `docs/plan/status/D0*.md`, `docs/knowledge/D0*.md`) where the backup's procedure may not be the 2016 one: e.g. D02's `p_Char_GetAllData` 37th column (D02-B19), the result codes −1091 / −1092 / −1094 the Character server handles for `usp_Character_setStatPoint` but the source does not produce, the 2016 `tCharacterLoading` columns.
- The table schema: merge the table → column lists of `docs/knowledge/D01.md`–`D05.md` into one schema, with types from the ODBC bind and fetch types (C type −16 i32, −28 u8, −17 u16, −18 u32, −25 i64, −27 u64, 1 string, −2 binary, 11 timestamp; `docs/knowledge/D02.md` lists the getters), keys and the constraint names `bak.py names` shows.
- Evidence for a procedure without source, strongest first: the call site (parameter count, C and SQL types, bind direction 1 in / 2 in-out / 4 out, the result columns the code fetches and their order; read the wrapper `SQL_<procedure>` and its callers, and the assembly with `/usr/bin/objdump -d -M intel` when the decompiler loses arguments); how the handler maps the return codes (client texts via `docs/protocol/client-error-codes.json`); procedures of the same family in the backups (same prefix, author header, tables); the 2017 PDB struct the result goes into; captures; the 2015 binaries for an older call (diffing only).
- Several versions of a procedure: compare `bak.py proc` of Character.bak, w00_Character.bak and `Fixes/*.sql` with what the 2016 binary passes, and say which version a rebuild should follow and why.
- If Docker or a Windows SQL Server is available, restoring the backups (SQL Server 2017 or newer) gives the real schema, defaults and constraints, which `bak.py` cannot extract. Record in the status file whether it was done.
- One block per procedure instead of per handler: signature with types and directions, tables and columns read and written, return codes and result rows, the calling handlers (`@ FUN_…`, link to the D0x section), and for each statement what it is inferred from. Do not edit D01–D05 outputs; corrections go into `docs/knowledge/D06.md` under "Corrections".

## Done when

Every procedure in scope and every run-time call string has a block (or a note that nothing can be inferred, with the reason); the schema lists every table the 2016 servers use; each open DB statement of D01–D05 is confirmed, corrected or left open with a reason.

## How to work

**One part per session.** Context is re-read on every turn, so a long session costs far more than several short ones.
This item has no scope table: in the first session, split the work into parts of similar size (about 2500 decompiled lines each, plus a sweep part and a review part) and write the list into the status file. At the start, read `docs/plan/status/D06.md` (its **State** line and **Working notes**) and take the first part
not done (no status file: part 1). Do only that part, close it (step 6) and end the session, even if context is left.

1. `AGENTS.md` is already in your context (do not re-read it); follow its **Context budget** section. Part 1 only: read
   `docs/plan/00-master-plan.md`. Later parts: the status file's working notes replace it; do not re-derive what they record.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for this part: the `docs/knowledge/*.md` sections of the items you depend on that touch it, and the
   `opcodes-*.md` / `packets-*.md` rows of its opcodes (one `rg -i -M 300 -e 0x<op> -e 0x<op> …
   docs/protocol/packets-<bin>.md` for all of them). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need. This
   includes your own output file: from part 2 on, never read it whole; use its outline and the sections you extend.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_(<NAME>|<NAME>)$'` (one regex for
   several; field names, offsets, sizes; also server-internal packets and shared enums/structs). It is a newer build:
   confirm against the 2016 code and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For the handlers of this part, in scope-table order, a few related handlers (one opcode family) at a time:
   - read them together: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin>
     <addr> <addr> …` (the only way to read code; never `sed`/`cat` on `decomp.c`). Registrations and sends of all of
     them in one query: `jq -c '.tables[].entries[] | select(.handler|IN("<FUN_…>","<FUN_…>"))' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate), again several per `clean.py` call
   - write their pseudocode blocks (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/D06.json`) and verified layouts (`docs/protocol/annotations/D06.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants. Write each
   in the part that first reaches it and note it in the working notes so later parts link to it instead of re-reading.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. The sweep part then checks for what was missed: `rg` your
   subsystem's strings, SHN tables and opcodes (`opcodes.json`) for functions never opened, check every caller and callee
   of the documented functions, and every unnamed `FUN_` left in the text, and run
   `python3 -I tools/protocol-re/coverage.py D06` (functions reachable from your handlers that no doc cites yet,
   largest first; cite each one you cover as `FUN_…` so it counts). Stopping early because the handlers are
   "done" is the most common gap in past items; reviews keep finding uncovered cases that were in scope.
6. Close the part: update `docs/plan/status/D06.md`. Its first line is `**State:** part <n> of <total> done` (or
   `**State:** done` after the review part). Then: done handlers per part, remaining work, and **Working notes**: only what
   later parts need and cannot cheaply re-read (struct and member offsets, helper names and meanings, shared state, open
   questions for a later part, next free bug ID `D06-B<n>`). Keep the notes short; every later session reads them.
   Commit on the current branch (`D06 part <n>: <what>`), then end the session. If context runs low before the part is
   done, finish the handler in hand, record the rest of the part as remaining, commit and end the same way.
   **Re-split when the parts are wrong.** The Parts table is sized from handler lines only; work outside the handlers
   (internals, tables, timers, the "also" list) is not counted. If a part still open looks too big for one session (or
   two are small enough to merge), write the new split as a **Parts** list in the status file (e.g. add part `3b`, with
   what it covers) and use its count as `<total>`; from then on the status file's list replaces the table. Do not edit
   this plan file (it is generated).
7. Sweep part, at the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/D06.md` (facts others need), add the
   original-server bugs table and an "uncertain / not reconstructed" section to your output.
8. Also end your output with a "Coverage boundary" section: one row per thing you found but did not cover (function,
   packet, table, behaviour) with an argument why it is out of bounds for this item: either the existing item that
   covers it (ID and the line of its plan or scope table that includes it) or, if no item does, a new follow-up item
   you create yourself (after `rg` in `docs/plan/items/*.md` and `make_plans.py` confirms no item, open or planned,
   covers it): add a `dict(id=…)` to `ITEMS` in `tools/protocol-re/make_plans.py` (next free ID of its area; title ends
   "(added by D06)"; goal, steps naming the functions/§ to start from, done), run `python3 -I tools/protocol-re/make_plans.py`,
   add its row to the item table and the order list in `docs/plan/00-master-plan.md`, list it in
   `docs/plan/status/D06.md` under "Follow-up items created", and name it in the boundary row (example: commit bcb1031, W05 added by W04). "Too large" or "ran out of context" is not out of bounds: that is unfinished work for the status file.
   **Never hand work to a finished item.** Before naming an item, read the first line of its status file. If it is
   `**State:** done`, name it only when its output already documents the thing (cite the §); nobody will reopen it.
   Otherwise: a small gap (a function, a packet layout, a code meaning; under ~1 h of work) you document now in your
   own output; a larger one becomes a new follow-up item as above, never a row pointing at the done item.
9. Review part: **review with fresh context** before marking the item done. The reviewer must not share your reading
   of the code. The review task is `docs/plan/review-prompt.md` (with `<ID>` = `D06`).
   - If your agent tool can start a fresh-context subagent (not a fork of your session), give it that file's text with
     `<ID>` replaced by `D06`, and wait for its numbered findings list.
   - Otherwise stop here: set the status file to "awaiting review" and end the session. The user runs the review as a
     separate session ("Review work item D06 as described in `docs/plan/review-prompt.md`") and then resumes this item,
     whose session finds the findings under "Review findings" in `docs/plan/status/D06.md`.
   Fix every finding in your files, or write in `docs/plan/status/D06.md` under "Review" why you reject it. Re-run
   `coverage.py D06` and `regen.sh`, record the before/after coverage line in the status file, then mark the item done.

## Rules

- Only write your own files: `docs/pseudocode/db/D06-db-inferred.md`, `docs/knowledge/D06.md`, `docs/plan/status/D06.md`,
  `tools/protocol-re/names/<bin>/D06.json`, `docs/protocol/annotations/D06.json`.
  Exception: creating a follow-up item (step 8) adds to `make_plans.py`, `docs/plan/items/` and `00-master-plan.md`;
  never change existing items there.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- Never leave a half-documented handler at the end of a session; list unfinished ones in the status file.
