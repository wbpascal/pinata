# Z15: Zone: quest script engine (added by Z08)

**Phase:** 2 · **Depends on:** Z08 · **Output:** `docs/pseudocode/zone/Z15-quest-engine.md`

## Goal

Z08 §3 documented the quest packets and DB answers and listed the script commands by number, but not the engine that runs them. Reconstruct the quest data, the script interpreter and the reward path well enough that a rebuild can run the original quest scripts.

## Item-specific guidance

- Read `docs/pseudocode/zone/Z08-content.md` §3 and §15 first. The 2017 PDB has the shared quest library (`CQuest`, `CQuestData`, `STRUCT_QSC` and its `Data` union, `QUEST_SCRIPT_COMMAND`, `PLAYER_QUEST_INFO`, `PLAYER_QUEST_DATA`); the client runs the same library, so compare the client functions (`pdb.py publics 'CQuest'`).
- Quest data: which file the zone loads (Z01 §2.3 loader list), the row layout read through `QuestData_Find` FUN_00635ff0 (fields Z08 used: +0x12 repeatable, +0x19/+0x1d/+0x1e/+0x20/+0x58/+0x5e start/end NPC flags), and how a quest's script is stored and found (`QuestScriptRun` FUN_005c0080, runner at CQuestZone+0xb8, `QuestScript_Next` FUN_006387f0).
- The interpreter: every `QUEST_SCRIPT_COMMAND` with its `Data` fields: IF/GOTO/MARK/SET/ADD/SUB and the script variables (CQuestZone+0xd0…), the GET_PLAYER_* getters (quest vt 0x64…0x78), SET/RESET/IS_ABSTATE, GET_ITEM_LOT, SCENARIO (`QuestPlayer_ScenarioRun` / `ScenarioDone_Server`, 0x440C), CALLPS (`PsStart` / `PsEnd`).
- Conditions and diary updates: FUN_0062fee0 (accept), FUN_006300d0 (done), FUN_00630570 (select start), FUN_006304d0 (give up), FUN_006304a0 (status), FUN_0062f3b0/4b0/550/5b0/680 and FUN_006302b0 (status changes), the 40-entry limit, daily/weekly/monthly/yearly repeat and the reset times of 0x441C.
- Rewards: `QuestCheckReward`, `QuestCheckSelectReward`, `QuestCheckRewardInven`, `QuestTakeReward` FUN_005bbe60 and the 0x441A NC_QUEST_DB_DONE_REQ body (money, exp, fame, character-title element, item creates, inventory lock `icl_QuestReward` / `InvenCellReleaser_QuestReward`).
- Other entry points: NPC click (`QuestPlayer_NPCClick` / `NPCClickCheck`, from Z02's NPC menu path), mob kill (`QuestActionMobKill`, `QuestPlayer_NPCMobKill`, `ShineQuestDiary_sqd_MobDead`, 0x440D NOTIFY_MOB_KILL), party quest checks (`PartyManufacture_pm_QuestCheck_*`), quest items (`sp_QuestItemGet`, `IsQuestDropItem`), the GM commands `&queststart`, `&questread`, `&questcomplete`, `&questrecieve`, `&questgiveup` (Z11 lists them).
- Settle Z08-B6 (silent give-up refusal) and give the meaning of every quest error number 0xB41…0xC10.

## Done when

Every script command and every condition function documented; quest data file and row layout named; the reward path from DONE to 0x441B written as pseudocode.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/Z15.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/Z15.json`) and verified layouts (`docs/protocol/annotations/Z15.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/Z15.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/Z15.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.

## Rules

- Only write your own files: `docs/pseudocode/zone/Z15-quest-engine.md`, `docs/knowledge/Z15.md`, `docs/plan/status/Z15.md`,
  `tools/protocol-re/names/<bin>/Z15.json`, `docs/protocol/annotations/Z15.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
