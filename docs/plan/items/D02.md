**Phase:** 2 · **Depends on:** nothing (can start immediately) · **Output:** `docs/pseudocode/db/D02-character.md`

## Goal

Character/avatar create/delete/list, full character load (NC_CHAR_CHARDATA) and save (CHARSAVE). Document each stored procedure and the column order (SQLGetData C types: -28 u8, -17 i16, -16 i32, -18 u32, 11 timestamp, 1 string). The 130-byte AVATAR record builder `FUN_0046bff0` is already decoded (annotations.json).

## Item-specific guidance

- **Database backups:** read `docs/plan/db-backups.md` first (which backup is which, which version to trust). Start with `python3 -I tools/protocol-re/bak.py cover <bin>`: it lists every procedure your server calls, the backups and `Fixes/` scripts that have it, and whether the parameter count matches. For every procedure you document, print its source (`bak.py Files/Server/2016/_Database/<file>.bak proc <name>`; compare the versions when several backups have it) and use it for the tables and columns touched, the result-set column order and the meaning of each return code (the Korean header comments list them). The backups come from private servers and are not the 2016 build: confirm against the binary (parameter count of the `{CALL …}` string, `SQLGetData` order and C types, result codes checked) and mark facts only a backup shows *(db-backup)*. Say which version you used, and flag procedures that exist only as private-server work. Name tables and columns only as the procedure source spells them.
- Character server: `Character.bak` (older, 2008 R2) and `w00_Character.bak` (newer, 2017, private-server fixes applied) together have 296 of the 311 procedures it calls, 294 with the same parameter count. In your area: `usp_CharacterLoading` takes 11 parameters in the binary but 6 in both backups; missing are `usp_CharacterLoadingDetailInfo`, `p_Promotion_Get`, `p_Promotion_Set`, `p_IsPromotionUser`. - Write the table list you meet (table → columns as the procedures use them) into `docs/knowledge/D02.md`; D03 and D04 build on it.
- Open from Z07 (§5): the zone never sets the wedding partner itself; `Partner.RegisterNumber` arrives only in `0x1081 NC_CHAR_WEDDINGDATA_ACK`. Find how the Character server chooses and stores the partner before a proposal (0x1080 / 0x1083 and their procedures), and when the divorce requests 0x1089 / 0x108B / 0x108D answer Success 0 (the zone has already taken the 250 000 / 750 000 fee and does not refund it, Z07-B11).

## How to work

1. `CLAUDE.md` is already in your context (do not re-read it); follow its **Context budget** section. Read
   `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for your area: `docs/plan/status/D02.md` (resume from it if present), the `docs/knowledge/*.md`
   of the items you depend on, and the `opcodes-*.md` / `packets-*.md` rows of your opcodes
   (`rg -i -M 300 '0x<op>' docs/protocol/packets-<bin>.md`). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
     (the only way to read code; never `sed`/`cat` on `decomp.c`). Its registration and sends:
     `jq -c '.tables[].entries[] | select(.handler=="<FUN_…>")' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/D02.json`) and verified layouts (`docs/protocol/annotations/D02.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/D02.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/D02.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
