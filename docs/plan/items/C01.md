# C01: Client packet-handler inventory

**Phase:** 1 · **Depends on:** nothing (can start immediately) · **Output:** `docs/knowledge/C01.md + re-data/client-handlers.json`

## Goal

Map every packet the 2016 client accepts: for each client scene/state (login, world/char select, in-game, …) find its dispatcher, list (opcode → client function), and describe briefly what the client does with each packet (fields read, UI text shown, state changed). This names most server→client opcodes and is the cross-reference every other item uses.

## Item-specific guidance

- Start from the known login-scene dispatcher `FUN_0046f4d0` (switch on dept, cmd). Find sibling dispatchers with the same shape (callers of the same network-receive path, switches on `>> 10` / `& 0x3ff`, functions `FUN_004aaa40`, `FUN_00665920`, `FUN_00666ce0`, `FUN_00546270` are candidates for the game scene).
- Write `re-data/client-handlers.json`: `{"0xOPCODE": {"scene": …, "func": "FUN_…", "summary": …, "fields": [[off, type, name, note]], "texts": [text ids → strings]}}`.
- Use the 16 `On_NC_*` debug strings and client RTTI `ProtoStruct<PROTO_NC_…>` names to name opcodes (`grep -n 'NC_' re-data/exports/client/strings.tsv`).
- Resolve text ids with `tools/protocol-re/shn.py` on `TextData*.shn`, and error codes with `client-error-codes.json`.
- Extend `tools/protocol-re/catalog.py` (or add a small script) so names from `client-handlers.json` flow into `opcodes.json` with source `client`, then run `regen.sh`.
- Summarise per scene in `docs/knowledge/C01.md` (dispatcher address, opcode list, notable behaviour).

## Done when

Every client dispatcher found; ≥90 % of opcodes the zone/WM send to clients mapped to a client function; names fed back into the generated docs.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/C01.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/C01.json`) and verified layouts (`docs/protocol/annotations/C01.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/C01.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/C01.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.

## Rules

- Only write your own files: `docs/knowledge/C01.md + re-data/client-handlers.json`, `docs/knowledge/C01.md`, `docs/plan/status/C01.md`,
  `tools/protocol-re/names/<bin>/C01.json`, `docs/protocol/annotations/C01.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
