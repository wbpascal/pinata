# X02: Confidence review and targeted capture/DB experiments

**Phase:** 3 · **Depends on:** all phase-2 items, X01 (soft) · **Output:** `docs/review/confidence.md + docs/plan/capture-scenarios.md`

## Goal

User review of finished items has corrected several assumptions per item, so the static analysis is only low-to-medium confidence. Re-check the claims everything else depends on, give each section a confidence rating, and turn whatever static reading cannot settle into concrete capture scenarios (beyond the 13 in `capture-guide.md`), many of them set up with direct database edits so an effect shows up in one short session.

## Item-specific guidance

- Learn from past mistakes first. Collect every correction made so far: the `Correction` sections in `docs/knowledge/*.md`, the corrected or contradicted entries in `docs/protocol/capture-validation.md`, and `git log -p` on `docs/pseudocode` and `docs/knowledge` (commits after an item's first commit are mostly corrections after user review). Group them into error classes (for example: a field's meaning guessed from its size, the wrong branch of a switch, a PDB 2017 fact taken for 2016, a struct offset off by the `ref` prefix, a callee assumed to do what its name says, a client handler not checked). Write the classes with counts to `docs/review/confidence.md` §1. They decide what to re-check.
- Rate every pseudocode section (per `docs/pseudocode/**/*.md` heading, and per `docs/knowledge/*.md` struct table): **high** = read in code and confirmed by a capture or by the client handler; **medium** = read in code only; **low** = *(inferred)*, *(pdb2017)* only, or one of the error classes from §1 applies. One table per file in §2: section, rating, reason, what would raise it.
- Adversarial re-check of the load-bearing claims, worst first: claims many other items cite (shared structs, the `ref` prefix, player-object offsets, ITEMDB message order, zone↔WM handoff), every low rating in a client-facing packet, and every instance of an error class from §1. For each, re-read the function with `clean.py`, then try to disprove the claim, not confirm it (check the other branches, the callers, the client side, and the 2015 binaries if behaviour looks odd). Record the result in §3: confirmed / corrected (with the correct statement and `@ FUN_…`) / still open. Do not edit other items' files; corrections go to `docs/knowledge/X02.md` §0 in the same table format as `docs/knowledge/Z07.md` §0, so X01 and the owners pick them up.
- Capture scenarios: for every claim still medium or low after the re-check, write a scenario in `docs/plan/capture-scenarios.md` (numbered from 14, continuing `capture-guide.md`). Each has: claims it tests (doc + section), setup, exact steps for the user, the **prediction** (opcodes in order with the field values our docs expect), and what result would disprove it. Group scenarios so one session covers several claims; order by claims settled per minute of user time.
- Database setups: where a state is slow to reach in play (high level, rare item, full inventory, guild with N members, quest at step K, money near the cap, expired item, banned/blocked account, character in a deleted or odd state), give the SQL that puts a test character in that state. Use only real table, column and procedure names, read from the backups (`bak.py`, `docs/plan/db-backups.md`) and checked against the 2016 binaries' `{CALL …}` strings; never guess a column. Each setup states which server must be stopped or which character must be logged out first (find where the Character/Account server caches the row), a `SELECT` to save the old values and the `UPDATE` that restores them, and a warning to run it on the test server only. Also use GM commands (`docs/pseudocode/zone/Z11-*.md`) where they reach the state faster than SQL, and boundary values (0, max, max+1, negative, wrong type id) to test the checks the docs describe.
- Also list in `capture-scenarios.md` the experiments that need a modified SHN table or server config (`Files/Server/2016/9Data`) instead of SQL, with the exact row/key to change.
- Items finished before the plan files had the "Coverage boundary" and review steps (status files without a "Review" section): run `coverage.py <ID>` for each, and add their uncovered, unargued gaps to `docs/review/confidence.md` §4 per item, so a follow-up session of that item can close them.
- Link the new scenarios from `docs/plan/capture-guide.md` (one line under the scenarios table; that is the only edit to another file). After the user records them, P02 validates them as usual; then re-run X02 to update the ratings.

## Done when

Every pseudocode section has a rating; all high-traffic claims re-checked with results in §3 and corrections in `docs/knowledge/X02.md`; every remaining medium/low client-facing claim has a scenario with a prediction; DB setups use only verified names and come with restore statements.

## How to work

1. `CLAUDE.md` is already in your context (do not re-read it); follow its **Context budget** section. Read
   `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for your area: `docs/plan/status/X02.md` (resume from it if present), the `docs/knowledge/*.md`
   of the items you depend on, and the `opcodes-*.md` / `packets-*.md` rows of your opcodes
   (`rg -i -M 300 '0x<op>' docs/protocol/packets-<bin>.md`). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
     (the only way to read code; never `sed`/`cat` on `decomp.c`). Its registration and sends:
     `jq -c '.tables[].entries[] | select(.handler=="<FUN_…>")' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/X02.json`) and verified layouts (`docs/protocol/annotations/X02.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. Before you finish, sweep for what you missed: `rg` your subsystem's
   strings, SHN tables and opcodes (`opcodes.json`) for functions you never opened, check every caller and callee of the
   functions you documented, and every unnamed `FUN_` left in your text, and run
   `python3 -I tools/protocol-re/coverage.py X02` (functions reachable from your handlers that no doc cites yet,
   largest first; cite each one you cover as `FUN_…` so it counts). Stopping early because the handlers are
   "done" is the most common gap in past items; reviews keep finding uncovered cases that were in scope.
6. Every ~10 handlers, update `docs/plan/status/X02.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/X02.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.
8. Also end your output with a "Coverage boundary" section: one row per thing you found but did not cover (function,
   packet, table, behaviour) with an argument why it is out of bounds for this item: either the existing item that
   covers it (ID and the line of its plan or scope table that includes it) or, if no item does, a proposed new item
   (title, scope, why it does not fit here) added to `docs/plan/status/X02.md` under "Proposed follow-up items" for the
   user to accept. "Too large" or "ran out of context" is not out of bounds: that is unfinished work for the status file.
9. **Review with fresh context** before marking the item done. Spawn one reviewer agent (Agent tool, a new
   general-purpose agent, not a fork: it must not share your reading of the code). Give it this plan file, your output
   files, and the output of `coverage.py X02 --all`, and ask it to find what is missing or wrong, not to confirm:
   - for each coverage gap: in scope and must be documented, or correctly outside (which item covers it)?
   - each "Coverage boundary" row: does the named item's plan or scope table really include it? Is the argument sound?
   - scope-table handlers, packets, error codes and client cross-checks that are thin or absent
   - re-read 5–10 of your claims in the code (`clean.py`), preferring *(inferred)* ones and field meanings, and report any
     that the code contradicts
   - it returns a numbered findings list and edits nothing.
   Fix every finding in your files, or write in `docs/plan/status/X02.md` under "Review" why you reject it. Re-run
   `coverage.py X02` and `regen.sh`, record the before/after coverage line in the status file, then mark the item done.

## Rules

- Only write your own files: `docs/review/confidence.md + docs/plan/capture-scenarios.md`, `docs/knowledge/X02.md`, `docs/plan/status/X02.md`,
  `tools/protocol-re/names/<bin>/X02.json`, `docs/protocol/annotations/X02.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
