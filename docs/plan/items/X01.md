# X01: Integration and review

**Phase:** 3 · **Depends on:** all · **Output:** `docs/pseudocode/README.md`

## Goal

Read all item outputs, fix contradictions, write the architecture overview (processes, links, data flow), a cross-server sequence index (feature → messages → handlers in each server), a glossary, a register of original-server bugs, and regenerate all docs. List remaining gaps.

## Item-specific guidance

- Original-server bug register: a section "Original-server bugs" in `docs/pseudocode/README.md` that lists every behaviour of the 2016 servers that looks unintended, so a rebuild can decide per entry to reproduce or fix it. One table row per bug: ID, server and handler (`@ FUN_…`, link to the pseudocode section), the 2016 behaviour, the visible effect, the likely intent, evidence level (read in code / *(inferred)* / *(captured)*) and the owning item. Keep the items' IDs (`<item>-B<n>`). Sources: each item's "Original-server bugs" section and every `(original bug)` tag (CLAUDE.md convention; W02-party-raid.md §9 is the reference). Items done before that convention (L00, W01, Z01–Z03, C01, C02, P01, P03) left free-text notes instead: grep `docs/pseudocode/**/*.md` and `docs/knowledge/*.md` for `bug`, `sic`, `never reach`, `uninitialised`, `not initialised`, `ignored`, `copy-paste`, `typo` and give those entries IDs `<item>-B<n>`. Include client-side mismatches (server sends a code or opcode the client does not handle) and client text typos. Do not change the owning items' files; if an entry needs more evidence, list it as a gap.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/X01.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/X01.json`) and verified layouts (`docs/protocol/annotations/X01.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/X01.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/X01.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.

## Rules

- Only write your own files: `docs/pseudocode/README.md`, `docs/knowledge/X01.md`, `docs/plan/status/X01.md`,
  `tools/protocol-re/names/<bin>/X01.json`, `docs/protocol/annotations/X01.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
