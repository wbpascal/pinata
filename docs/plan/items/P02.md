# P02: Capture validation (run once per batch of captures)

**Phase:** 2 · **Depends on:** P01, captures in re-data/captures/ · **Output:** `docs/protocol/capture-validation.md`

## Goal

Use real captures to confirm or correct the documented packet layouts, value ranges, error codes and message order. Re-run this item whenever new captures are added or a phase of items finishes.

## Item-specific guidance

- Run `tools/protocol-re/pcap_decode.py` on every capture in `re-data/captures/` that has not yet been processed (keep a list in `docs/plan/status/P02.md`). Use the packet comments inside each capture (shown as markers by the decoder) and the scenario notes next to it (see `docs/plan/capture-guide.md`).
- For each opcode seen: compare with annotations and generated layouts. Confirmed fields → add `"evidence": "capture:<file>"` to the field note in `docs/protocol/annotations/P02.json`. Name fields from what changes between scenarios (e.g. level, coordinates, item ids against the SHN tables).
- Message order: check the sequences in `docs/protocol/README.md` §2 and the pseudocode (e.g. login burst after 0x1803) against the captured order. Record differences.
- Write `docs/protocol/capture-validation.md`: per opcode the status (confirmed / corrected / contradicted / never seen), and a list of discrepancies addressed to the owning work item (look up the opcode in `docs/plan/items/*.md`).
- Do not edit other items' pseudocode. Report contradictions in `capture-validation.md` and in `docs/knowledge/P02.md`.

## Done when

All captures processed; every observed opcode has a status; discrepancies listed per work item.

## How to work

1. Read `CLAUDE.md` (shared conventions, tools, established facts) and `docs/plan/00-master-plan.md`.
2. Read `docs/pseudocode/login-server.md`: it is the format and depth to match.
3. Read what exists for your area: `docs/knowledge/*.md` of the items you depend on, `docs/plan/status/P02.md`
   (resume from it if present), the generated `docs/protocol/opcodes-*.md` / `packets-*.md` rows for your opcodes.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_<NAME>$'` (field names, offsets,
   sizes; also server-internal packets and shared enums/structs). It is a newer build: confirm against the 2016 code
   and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For each handler in the scope table, in order:
   - read it: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin> <addr>`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate)
   - write its pseudocode block (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/P02.json`) and verified layouts (`docs/protocol/annotations/P02.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants.
6. Every ~10 handlers, update `docs/plan/status/P02.md` (done / remaining). Before you run low on context,
   write the status so a fresh session can continue.
7. At the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/P02.md` (facts others need), add an
   "uncertain / not reconstructed" section to your output, and mark the item done in the status file.

## Rules

- Only write your own files: `docs/protocol/capture-validation.md`, `docs/knowledge/P02.md`, `docs/plan/status/P02.md`,
  `tools/protocol-re/names/<bin>/P02.json`, `docs/protocol/annotations/P02.json`.
- Mark deductions *(inferred)*. Never invent names; derive them from strings, client texts, or label them as ours.
- If the scope is too large for one session, finish complete handlers. Never leave a half-documented one.
  List the rest in the status file.
