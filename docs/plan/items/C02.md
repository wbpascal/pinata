# C02: 2017 client PDB: official opcode names, packet structs, types, client function names

**Phase:** 1 · **Depends on:** C01 (soft) · **Output:** `docs/knowledge/C02.md + docs/protocol/pdb-layouts.json + names/client/C02.json`

## Goal

`Files/Client/2017/Fiesta.pdb` is the full private PDB of a slightly newer client (`patch_2017_08_p01`; GUID matches `Files/Client/2017/Fiesta.bin`). It holds the official protocol enums (`PROTOCOL_COMMAND` = dept, `PROTOCOL_COMMAND_<DEPT>` = cmd → 2600 opcode names), 2718 `PROTO_NC_*` packet structs with field names, offsets and sizes (538 of them DB/server-internal), shared types (`SHINE_ITEM_ATTRIBUTE` + 38 `ShineItemAttr_*`, `CHAR_PARAMETER_DATA`, `PROTO_AVATARINFORMATION`, enum `ABSTATEINDEX` (823 abstates), `ChrClassType`, 134 SHN row structs `<Table>::DataVersion`) and 30909 client function names. Turn it into evidence every item can use, without letting 2017 facts overwrite verified 2016 facts.

## Item-specific guidance

- Reader: `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types|publics|json …` (stdlib, ~1 s). Opcode table = for each `NC_<X>` in enum `PROTOCOL_COMMAND`, the members of `PROTOCOL_COMMAND_<X>`; opcode = dept<<10 | cmd. 11 depts have no cmd enum (KQ, WT, CT, HOLY_PROMISE, AUCTION, …).
- Opcode names: feed them into `catalog.py` as name source `pdb2017`, ranked below `handler`/`client` and above `inferred(REQ+1)` and log literals. Measured against `opcodes.json` (2016 binaries): 1347 unnamed opcodes get a name, 933 agree, 110 conflict (51 `handler`, 41 `inferred(REQ+1)`, 18 log literals), 182 2016 opcodes are not in the 2017 enums, 210 2017 opcodes are not in the 2016 binaries. Conflicts are scattered, not a per-dept shift, so check each one in the 2016 code: several `handler` names come from one handler registered for two opcodes (e.g. zone `0x9884`/`0x9885` both named `…_DEPOSIT_RNG`), where the PDB name is the better one. Record the verdict per conflict in `docs/knowledge/C02.md`.
- Layouts: write `docs/protocol/pdb-layouts.json` (opcode → struct name, size, flattened fields `[offset, type, name]`, nested structs and arrays expanded one level) and make `packets.py`, `pcap_decode.py` and `make_dissector.py` use it as a source between hand annotations and generated `layouts.json` (label it `pdb2017`). Compare each struct size with the 2016 handler's length check / send size (`layouts.json`) and list mismatches (version drift) in the knowledge file. Server-internal packets about a player carry a 6-byte `ref` prefix that is **not** part of the PROTO struct (`docs/knowledge/Z01.md`): PDB offset = 2016 payload offset − 6.
- Hand annotations already made (L00 `annotations.json`, C01, W01, Z01): 96 of 112 with a PDB struct match the flattened PDB offsets; the rest are the `ref` prefix (W01/Z01 S2S packets), the 2-byte prefix in W01 `0x0c13`, `0x0C5A` (`sUserName` is 260 bytes, so our `unused` at 256 is the name's tail) and `0x0C66` (1-byte struct). Report per owning item; do not edit their files.
- Types catalogue in `docs/knowledge/C02.md`: which PDB types matter to which item (Z03 `ABSTATEINDEX`, Z04/Z05 `ShineItemAttr_*` and `SHINE_ITEM_STRUCT`, Z07 `CHAR_PARAMETER_DATA`, W01/D02 `PROTO_AVATARINFORMATION`, SHN row structs vs `shn.py` column names, enums such as `ITEM_LOOT_TYPE`, `PLAYER_QUEST_STATUS`, `GUILD_HISTORY_MSG_TYPE`). Point to the `pdb.py types REGEX` command instead of copying large dumps.
- Client function names: import `Files/Client/2017/Fiesta.bin` into `re-data/ghidra` as project `client2017` with the PDB applied (headless, PDB Universal analyzer, PDB next to the exe) and export it to `re-data/exports/client2017/` like the others. Port names to the 2016 client: first the `On_NC_*` handlers by opcode (same opcode → same handler in the scene dispatchers of both versions; 838 of C01's 901 handled opcodes have a 2017 name, 645 of them unnamed today), then callees and classes by call-graph / byte matching. Write `tools/protocol-re/names/client/C02.json`; mark ported names as `pdb2017` in the knowledge file.
- Evidence: a PDB fact applies to 2016 only after a 2016 binary agrees (same opcode in a handler table, same size check, same field use). Until then mark it *(pdb2017)* (see `AGENTS.md` evidence levels).

## Done when

PDB opcode names in `opcodes.json` with conflicts resolved; `pdb-layouts.json` used by the generated docs, decoder and dissector; 2016 client handlers named from the PDB; per-item follow-up list in `docs/knowledge/C02.md`.

## How to work

**One part per session.** Context is re-read on every turn, so a long session costs far more than several short ones.
This item has no scope table: in the first session, split the work into parts of similar size (about 2500 decompiled lines each, plus a sweep part and a review part) and write the list into the status file. At the start, read `docs/plan/status/C02.md` (its **State** line and **Working notes**) and take the first part
not done (no status file: part 1). Do only that part, close it (step 6) and end the session, even if context is left.

1. `AGENTS.md` is already in your context (do not re-read it); follow its **Context budget** section. Part 1 only: read
   `docs/plan/00-master-plan.md`. Later parts: the status file's working notes replace it; do not re-derive what they record.
2. Read `docs/pseudocode/FORMAT.md`: the format and depth to match (not the whole `login-server.md`).
3. Read what exists for this part: the `docs/knowledge/*.md` sections of the items you depend on that touch it, and the
   `opcodes-*.md` / `packets-*.md` rows of its opcodes (one `rg -i -M 300 -e 0x<op> -e 0x<op> …
   docs/protocol/packets-<bin>.md` for all of them). For docs over ~15 KB and every `§` reference above, run
   `python3 -I tools/protocol-re/sect.py <file>` for the outline, then `sect.py <file> <§|regex>` for what you need. This
   includes your own output file: from part 2 on, never read it whole; use its outline and the sections you extend.
   For each packet, also look up the official name and struct in the 2017 client PDB:
   `python3 -I tools/protocol-re/pdb.py Files/Client/2017/Fiesta.pdb types '^PROTO_NC_(<NAME>|<NAME>)$'` (one regex for
   several; field names, offsets, sizes; also server-internal packets and shared enums/structs). It is a newer build:
   confirm against the 2016 code and mark unconfirmed PDB facts *(pdb2017)*. Read `docs/knowledge/C02.md` if it exists.
4. For the handlers of this part, in scope-table order, a few related handlers (one opcode family) at a time:
   - read them together: `python3 -I tools/protocol-re/clean.py re-data/exports/<bin> tools/protocol-re/names/<bin>
     <addr> <addr> …` (the only way to read code; never `sed`/`cat` on `decomp.c`). Registrations and sends of all of
     them in one query: `jq -c '.tables[].entries[] | select(.handler|IN("<FUN_…>","<FUN_…>"))' re-data/exports/<bin>/handlers.json`
   - follow the callees that carry the logic (skip logging/profiling/container boilerplate), again several per `clean.py` call
   - write their pseudocode blocks (`@ FUN_…`), with field names, checks, state changes, replies, error codes
   - for client-facing packets, check the client handler (C01's `re-data/client-handlers.json` / `docs/knowledge/C01.md`
     if available; otherwise search the client export) and resolve codes via `docs/protocol/client-error-codes.json`
   - record new names (`names/<bin>/C02.json`) and verified layouts (`docs/protocol/annotations/C02.json`)
5. Beyond the handlers, document the subsystem itself: data structures, tables loaded, timers, invariants. Write each
   in the part that first reaches it and note it in the working notes so later parts link to it instead of re-reading.
   **Be exhaustive within your item.** The scope table is the starting point, not the boundary: follow every callee,
   branch, error path, timer, table and packet these handlers reach, plus the matching client handlers and DB procedures,
   until what remains clearly belongs to another item. The sweep part then checks for what was missed: `rg` your
   subsystem's strings, SHN tables and opcodes (`opcodes.json`) for functions never opened, check every caller and callee
   of the documented functions, and every unnamed `FUN_` left in the text, and run
   `python3 -I tools/protocol-re/coverage.py C02` (functions reachable from your handlers that no doc cites yet,
   largest first; cite each one you cover as `FUN_…` so it counts). Stopping early because the handlers are
   "done" is the most common gap in past items; reviews keep finding uncovered cases that were in scope.
6. Close the part: update `docs/plan/status/C02.md`. Its first line is `**State:** part <n> of <total> done` (or
   `**State:** done` after the review part). Then: done handlers per part, remaining work, and **Working notes**: only what
   later parts need and cannot cheaply re-read (struct and member offsets, helper names and meanings, shared state, open
   questions for a later part, next free bug ID `C02-B<n>`). Keep the notes short; every later session reads them.
   Commit on the current branch (`C02 part <n>: <what>`), then end the session. If context runs low before the part is
   done, finish the handler in hand, record the rest of the part as remaining, commit and end the same way.
7. Sweep part, at the end: run `tools/protocol-re/regen.sh`, write `docs/knowledge/C02.md` (facts others need), add the
   original-server bugs table and an "uncertain / not reconstructed" section to your output.
8. Also end your output with a "Coverage boundary" section: one row per thing you found but did not cover (function,
   packet, table, behaviour) with an argument why it is out of bounds for this item: either the existing item that
   covers it (ID and the line of its plan or scope table that includes it) or, if no item does, a proposed new item
   (title, scope, why it does not fit here) added to `docs/plan/status/C02.md` under "Proposed follow-up items" for the
   user to accept. "Too large" or "ran out of context" is not out of bounds: that is unfinished work for the status file.
9. Review part: **review with fresh context** before marking the item done. The reviewer must not share your reading
   of the code. The review task is `docs/plan/review-prompt.md` (with `<ID>` = `C02`).
   - If your agent tool can start a fresh-context subagent (not a fork of your session), give it that file's text with
     `<ID>` replaced by `C02`, and wait for its numbered findings list.
   - Otherwise stop here: set the status file to "awaiting review" and end the session. The user runs the review as a
     separate session ("Review work item C02 as described in `docs/plan/review-prompt.md`") and then resumes this item,
     whose session finds the findings under "Review findings" in `docs/plan/status/C02.md`.
   Fix every finding in your files, or write in `docs/plan/status/C02.md` under "Review" why you reject it. Re-run
   `coverage.py C02` and `regen.sh`, record the before/after coverage line in the status file, then mark the item done.
